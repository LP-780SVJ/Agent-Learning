# CodeTeam 代码架构

本文档是持续维护的架构说明，记录当前代码如何分层、每层负责什么、哪些边界不能穿透。

## 当前定位

CodeTeam 是一个本地优先、provider-neutral 的 coding agent runtime 学习项目。它目前已经具备：

- Agent loop、工具调用、最终输出语义校验、事件和用量统计。
- 仓库扫描、符号索引、ImportGraph、检索排序、Repo Map、上下文压缩。
- Git patch/worktree/checkpoint/diff/rollback。
- CommandPolicy、Approval、SafeExecutor、Docker sandbox。
- Task/Plan/Repair/Failure Recovery。
- Durable Session、pause/resume、event log。
- Week5 Multi-Agent foundation：Lead/Worker、TaskDAG、进程内 TaskScheduler、原子 task claim。
- CLI 产品入口：`run`、`resume`、`diff`、`rollback`、`inspect-repo`、`context`、`eval`。
- 检索 benchmark 和 Week4 任务评估设计。

## 关键边界

### CLI 层

CLI 只负责参数解析、请求 DTO、错误渲染和退出码。它不应该直接实现仓库检索、session 恢复、Docker policy 或 patch 逻辑。

### Application / Service 层

这一层编排多个 domain 模块。例如 `build_context.py` 把 RepositoryIndex、QueryAnalyzer、CandidateGenerator、FileRanker、RepoMap、InstructionLoader 和 Compressor 串起来。

### Agent Orchestrator

`SingleAgentOrchestrator` 负责状态推进和依赖编排，不应该实现底层 Git、Docker、LLM HTTP 或文件解析细节。

### Git 层

Git 层负责 workspace 状态和可恢复性：

- PatchValidator 先校验再应用。
- GitWorkspace 失败时验证没有半截副作用。
- WorktreeManager 做任务级隔离。
- CheckpointManager 做快速恢复。

### Execution / Sandbox 层

执行链路必须保持：

```text
CommandRequest -> CommandPolicy -> Approval -> SafeExecutor -> SandboxRunner
```

Policy 判断意图，Sandbox 限制能力。两者不能互相替代。

### Session 层

`session.json` 是 resume source of truth；`events.jsonl` 是 audit/debug/evaluation history。Session 不持久化 runtime object，只保存可重建配置和 durable state。

### Evaluation 层

Evaluation 是外部 judge，不应相信 agent final message。正式 task success 必须由 hidden acceptance、regression、安全和预算共同决定。

### Agent Team 层

`codeteam.agent_team` 是 Week5 的 Multi-Agent control plane，不直接执行工具或修改 workspace。

当前边界：

- `LeadAgent` 复用现有 `Planner`，输出 `LeadPlanningResult`。
- `WorkerAssignment` 是 planning-time contract，不保存 owner、attempt、failure reason。
- `TaskDAG` 是 topology source of truth，边使用 `TaskNode.node_id`。
- `TaskScheduler` 是进程内 runtime state source of truth，维护 `TaskRuntimeRecord.status`、owner、attempt、ready queue 和 Worker availability。
- `WorkerRegistry.compatible(role)` 只表示 role 匹配；Worker 是否空闲由 Scheduler runtime state 判断。
- Scheduler 事件走 `codeteam.events.AgentEventType`，不新增独立日志系统。

未覆盖边界：

- Day3 Scheduler 只证明线程级原子 claim，不证明跨进程/分布式锁。
- Worker crash、heartbeat、lost task recovery 留给后续 Week5。
- Mailbox、worktree ownership、merge/review 仍未接入。

## 已知架构缺口

- `codeteam run` 目前仍是产品化外壳，使用 `MockPlanner`，还不是完整真实 patch actor。
- 15-task hidden-oracle EvalRunner/Grader 尚未实现。
- Full mypy 存在历史 import-chain/stub/type debt。
- Full ruff 存在历史 style/lint debt，适合单独 cleanup 分支处理。
- Medium repo 暴露出 business behavior 和 cross-module retrieval 仍弱。

## 后续维护规则

- 新功能先明确所属层级，避免 CLI 或 orchestrator 吞掉底层职责。
- 新的安全能力必须同时说明 policy 边界和 sandbox 边界。
- 新的 agent 成功率必须来自外部 eval harness，不来自 agent 自我报告。
- 新 benchmark 必须保存 dataset、manifest、raw results 和 report。
- 大规模 lint/type cleanup 与功能修复分开提交，避免 review 噪声。

## 主要链路函数地图

本节记录当前系统最常走的函数链路、关键参数和返回对象。它的作用是帮助后续维护时快速判断“一个需求应该改哪一层”，也方便检查是否发生了层级穿透。

### 1. CLI 入口链路

CLI 主入口在 `codeteam/cli/app.py`，使用 Typer 将命令参数转成 request DTO 或 `argparse.Namespace`，再交给具体 command module。

```text
python -m codeteam.cli.app <command>
  -> codeteam.cli.app.<command>(...)
  -> request DTO / Namespace
  -> codeteam.cli.<xxx>_command.run_xxx(...)
```

主要入口函数：

```python
inspect_repo(path: Path = Path("."), output_format: CliOutputFormat = TEXT) -> None
context(query: str, path: Path = Path("."), top_k: int = 5, budget: int = 1024, output_format: CliOutputFormat = TEXT) -> None
eval_command(dataset: Path, repo: Path = Path("."), methods: str = "hybrid", output: Path = Path("evals/results/")) -> None
run(task: str, repo: Path = Path(".")) -> None
resume(session_id: str, repo: Path = Path("."), provider_id: str | None = None, model_id: str | None = None) -> None
diff(session_id: str, repo: Path = Path("."), base_ref: str = "HEAD", output_format: CliOutputFormat = TEXT) -> None
rollback(session_id: str, checkpoint_id: str, repo: Path = Path("."), output_format: CliOutputFormat = TEXT) -> None
main(argv: list[str] | None = None) -> None
```

CLI request DTO 在 `codeteam/cli/requests.py`：

```python
RunRequest(task: str, repo: Path = Path("."), output_format: Literal["text", "json"] = "text")
ResumeRequest(session_id: str, repo: Path = Path("."), output_format: Literal["text", "json"] = "text", provider_id: str | None = None, model_id: str | None = None)
DiffRequest(session_id: str, repo: Path = Path("."), base_ref: str = "HEAD", output_format: Literal["text", "json"] = "text")
RollbackRequest(session_id: str, checkpoint_id: str, repo: Path = Path("."), output_format: Literal["text", "json"] = "text")
```

边界规则：

- CLI 负责参数和退出码，不直接做检索、patch、Docker、session reconciliation。
- `--format` 这类非法用户输入应在 CLI 层变成 exit `2`，不能暴露 traceback。
- `resume --provider/--model` 目前 fail-closed，因为真实 override 链路尚未接完。

### 6. PlanStep 执行 / Patch / Repair 链路

`execute_plan_step()` 是后续真实 actor 要接入的关键函数。它已经具备验证与 repair 的基础结构，但目前没有被 CLI `run` 端到端接上。

入口签名：

```python
SingleAgentOrchestrator.execute_plan_step(
    *,
    task: TaskSpec,
    plan_step: PlanStep,
    task_state: TaskState,
    initial_patch: str,
    repair_agent: RepairAgent,
    target_request: VerificationRequest,
    related_regression_request: VerificationRequest | None = None,
```

```text
  -> run target verification
  -> if target passed, run related regression if configured
  -> if failed, RepairAgent.propose_patch(context)
  -> repeat until success / exhausted / interrupted
  -> StepExecutionResult
```

```python

```

```python

```

```python

```

- `RepairLoop` 不推进 task/session 状态。

- `VerificationService.verify()` 负责把验证请求变成安全执行结果。

### 8. Git Patch / Diff / Checkpoint / Rollback 链路

Git 层负责“代码如何安全改变”和“改变后如何恢复”。

Patch path：

```text
patch string
  -> GitWorkspace.check_patch(patch)
  -> PatchValidator.validate(patch)
```

### 9. Durable Session / Resume 链路

Session 是 Week4 的 durable state 中心。

```text

  -> JsonSessionStore.create(session)
  -> JsonSessionStore.append_event(SESSION_CREATED)

SessionService.pause(session, reason)
  -> stop_operation(session)
  -> refresher(session)
  -> JsonSessionStore.save(status=PAUSED)
  -> append_event(SESSION_PAUSED)
  -> release writer lock

SessionService.resume(session_id, current_repo)
  -> JsonSessionStore.load(session_id)
  -> SessionWriterLock.acquire()
  -> SessionReconciler.reconcile(session, current_repo)

  -> save(status=RUNNING)
  -> append_event(SESSION_RESUMED)
```

# Week5 Agent Team 控制面架构

Week5 在既有 Single-Agent Runtime 之外新增 Lead/Worker 控制面，但目前仍然只证明进程内调度基础，不执行真正多 Agent 并行改代码。

```text
TaskSpec
  -> LeadAgent.create_plan()
  -> Plan + WorkerAssignment
  -> TaskDAG.from_lead_planning_result()
  -> TaskScheduler.schedule()
  -> TaskScheduler.claim(worker_id)
  -> start / complete / fail
  -> AgentMailbox.send() / receive()
```

核心模块：

```text
codeteam/agent_team/models.py
  AgentIdentity / AgentInfo / AgentRole / AgentStatus
  WorkerAssignment / LeadPlanningResult

codeteam/agent_team/lead.py
  LeadAgent
  RoleAssigner
  DeterministicRoleAssigner

codeteam/agent_team/worker.py
  WorkerAgent
  WorkerRegistry

codeteam/agent_team/dag.py
  TaskStatus
  TaskNode
  TaskDAG

codeteam/agent_team/scheduler.py
  TaskRuntimeRecord
  TaskClaim
  SchedulerResult
  TaskScheduler
  TASK_TRANSITIONS

codeteam/agent_team/mailbox.py
  AgentMessageType
  AgentMessage
  AgentMailbox
  MailboxError / UnknownAgentError / DuplicateMessageError / MailboxFullError
```

状态所有权：

```text
TaskDAG
  负责 topology、node_id、dependencies 和构图校验。

TaskScheduler
  构造时复制 DAG topology。
  构造后不读取原 DAG status，也不接受动态 topology mutation。
  TaskRuntimeRecord.status 是运行时状态权威。

WorkerRegistry
  负责 worker identity / role 查询。
  不等于 worker availability source of truth。

TaskScheduler worker runtime map
  负责 READY/BUSY 等调度期 availability。

AgentMailbox
  负责 Agent 间通信地址簿、每 agent inbox、message_id 去重、容量和 FIFO。
  不负责 Scheduler status，不负责 Worker availability，不负责 durable replay。
  capacity_per_inbox 只限制当前 inbox backlog，不限制累计 seen IDs 或 event history。
```

Day3 hardening 后的关键边界：

```text
fresh DAG only
  TaskScheduler 构造时先调用 TaskDAG.validate()。
  未 validate 的 cycle/坏图会在 Scheduler 边界 fail fast。
  TaskScheduler 只接受全 PENDING DAG；resume 留给 Day6。

event transaction != event delivery
  状态、owner、attempt、queue 和内部 events 在锁内提交；
  event_sink 在锁外接收防御性副本；
  sink 普通异常只记录 scheduler.event_delivery_failed，不回滚状态。

missing compatible role
  schedule() 返回 waiting_for_worker，task 保持 PENDING；
  后续注册兼容 worker 后可再次 schedule。

immutable transition table
  公共 TASK_TRANSITIONS 是只读 mapping，值为 tuple。
```

Day4 Mailbox 后的关键边界：

```text
AgentMessage != AgentEvent != schemas.Message
  AgentMessage 是待消费通信载体；
  AgentEvent 是已发生审计事实；
  codeteam.schemas.messages.Message 是 LLM/tool 对话 schema。

Mailbox address book != WorkerRegistry
  Mailbox 允许 Lead 和 Worker 都注册；
  WorkerRegistry 只回答 role compatibility；
  AgentStatus.BUSY 不影响收件能力。

Mailbox communication != Scheduler state transition
  TASK_COMPLETED message 不会直接完成 task；
  complete/fail 仍必须通过 TaskScheduler owner/status 检查。

AgentMessage serialization
  payload 必须是 JSON-compatible dict；
  created_at 必须是 finite non-negative float；
  callable、自定义 object、NaN/inf 和非字符串 dict key 在模型构造时拒绝。

broadcast atomicity
  broadcast 批内生成的 message_id 必须唯一；
  批内重复、历史重复、未知 recipient 或容量满都会在任何入队前失败；
  不通过循环重试 UUID 掩盖碰撞。

event transaction != event delivery
  inbox/message_id/events 在锁内提交；
  event_sink 在锁外接收防御性副本；
  sink 普通异常只记录 mailbox.event_delivery_failed，不回滚消息。

memory retention tradeoff
  _seen_message_ids 随累计接受消息数增长；
  _events 随注册、发送、接收和投递失败事件增长；
  Day4 按 team/task/session 生命周期释放 Mailbox；
  去重窗口、事件归档、持久化和恢复策略留给 Day6。
```

当前不做：

```text
durable queue
Worker heartbeat
crash recovery
distributed lock
cross-process claim
cross-process mailbox
ack/nack
exactly-once
end-to-end multi-agent speedup
```
