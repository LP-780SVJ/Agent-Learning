## D01. 结构化工具调用协议

**Capability:** Agent Harness / Tool Runtime

**Code Location:** `codeteam/schemas/tool_calls.py`, `codeteam/tools/base.py`, `codeteam/tools/registry.py`, `tests/test_tool_models.py`, `tests/test_tool_registry.py`

**Function:** 用 Pydantic schema 表示 `ToolCall`、`ToolResult` 和工具定义，让模型输出不再是自由文本，而是可以校验、路由、执行和记录的结构化对象。

**Problem:** Coding Agent 如果直接解析自然语言里的“帮我读文件”“运行测试”，工具调用会变得不可预测：参数类型错了、工具名拼错了、错误无法结构化返回，Agent Loop 也无法稳定恢复。

**Design:** 工具调用被拆成三层：schema 层定义数据契约，tool 层定义工具行为，registry 层负责注册和执行。工具失败不会直接炸掉主循环，而是包装成结构化 `ToolResult`。

**Invariant:** 模型想调用工具，必须满足工具名存在、参数可校验、结果可结构化返回。

**Why This Way:** 这是 Agent Harness 的基础边界。LLM 负责提出意图，Runtime 负责验证意图是否符合工具契约。

**Alternatives:** 直接让模型输出 shell 命令最简单，但安全性和可观测性最差；函数调用 schema 更严格，但早期实现成本更高。当前方案选择了轻量 schema + registry，适合学习型 runtime。

**Verification:** 单元测试覆盖工具模型校验、注册、执行、未知工具、参数错误和结构化错误返回。

**Industrial Reference:** OpenAI Responses API 的工具调用、Claude Code / Cline 的工具执行，本质上也都需要把模型意图转成受控工具动作。OpenAI 的 `apply_patch` 文档也明确要求 patch harness 解释操作、应用补丁、记录成功状态和错误信息。

**Limitations:** 当前 registry 还比较轻量，没有工具权限分级、工具超时元数据、审计 ID、并发执行控制。

**Future Improvement:** 给每个工具增加 risk level、permission scope、timeout、side_effect 标记，并把工具执行事件接入 trace。

**Interview Version:** 我没有让模型直接“说要做什么”，而是把工具调用做成结构化协议。这样 Runtime 可以在执行前校验参数、在执行后记录结构化结果，失败也能回到 Agent Loop 继续处理。

**Likely Follow-ups:** 为什么不用纯 JSON dict？工具 schema 怎么版本化？如果模型输出多个工具调用怎么办？工具失败应该抛异常还是返回结果？

## D02. 最终输出语义校验

**Capability:** Agent Harness / Stop Conditions

**Code Location:** `codeteam/schemas/final_output.py`, `codeteam/agent_loop.py`, `tests/test_final_output_models.py`, `tests/test_final_output_semantics.py`

**Function:** 对模型最终输出进行结构校验和语义校验，尤其是不能只因为模型说 `completed` 就认为任务真的完成。

**Problem:** LLM 可能幻觉式宣布“完成了”，但测试没跑、错误还在、或者输出字段自相矛盾。如果 Agent Runtime 盲信 final answer，就会产生虚假的成功状态。

**Design:** `AgentFinalOutput` 用枚举和字段约束表达最终状态；`validate_final_output_semantics()` 进一步检查 status、tests_passed、error、user_input_request 之间的逻辑一致性。`run_agent_loop()` 在接收 final output 时必须经过该校验。

**Invariant:** Runtime 的完成状态由语义校验决定，不由模型口头声明决定。

**Why This Way:** Agent Harness 需要把“模型说完成”和“系统判定完成”分开，这是面向可靠性的关键设计。

**Alternatives:** 只要求模型输出自然语言总结最简单，但无法自动判断任务状态；只做 JSON schema 校验能防类型错误，但防不了逻辑矛盾。当前方案把结构和语义分开，边界更清楚。

**Verification:** 测试覆盖 completed / failed / needs_user_input 等状态组合，验证不一致输出会被拒绝。

**Industrial Reference:** 工业 Agent 通常会把模型输出和系统状态分开处理，例如工具调用结果、测试结果、审批结果都作为外部事实反馈给模型，而不是只相信文本回答。

**Limitations:** 当前语义规则仍比较简单，主要检查最终输出字段关系，还没有接入真实 test runner 的证据对象。

**Future Improvement:** 将测试命令、退出码、失败用例、diff 状态作为 final validation 的外部事实输入，形成更强的 completion gate。

**Interview Version:** 我做了一个 final output gate：模型可以说 completed，但 Runtime 会检查它的输出语义是否和测试状态、错误字段一致。这样可以避免 Agent 幻觉式宣布成功。

**Likely Follow-ups:** 如果测试没跑，能不能 completed？如果用户只要解释不改代码，怎么判断完成？语义校验规则会不会太死？

## D03. 文件工具的 workspace 边界和写前备份

**Capability:** Tool Runtime / Workspace Safety

**Code Location:** `codeteam/tools/files.py`, `tests/test_file_tools.py`

**Function:** 提供受控文件读写能力，限制访问 workspace 内路径，并在写文件前保存备份。

**Problem:** Coding Agent 需要改文件，但不能读写 workspace 外的用户文件，也不能一次错误写入就让用户无法恢复。

**Design:** 文件工具统一解析路径，检查路径是否在 workspace 内，防止 `..` 和符号链接逃逸；写入前创建备份，让修改具备最小恢复能力。

**Invariant:** 文件工具不能访问 workspace 外文件；写入行为必须可追踪，且至少保留修改前备份。

**Why This Way:** 这是从“脚本能改文件”升级到“Agent 可以安全改文件”的第一层边界。

**Alternatives:** 直接用 Python `open()` 最简单，但没有边界；OS sandbox 更强，但实现成本高。当前选择应用层路径边界，是学习项目早期的合理台阶。

**Verification:** 测试覆盖正常读写、路径逃逸、符号链接逃逸、文件大小限制和备份行为。

**Industrial Reference:** Codex 的 sandbox 模式把 `workspace-write` 定义为可读文件、可在 workspace 内编辑和运行本地命令；Cline 也强调文件写入和命令执行需要用户控制。CodeTeam 当前实现的是更轻量的应用层版本。

**Limitations:** 应用层边界不是 OS 级 sandbox；如果工具之外的命令能任意执行，仍可能绕过文件工具限制。

**Future Improvement:** 和 CommandPolicy、Docker sandbox、Git checkpoint 结合，形成“路径边界 + 命令审批 + 可回滚”的完整安全链。

**Interview Version:** 文件工具不是简单封装读写，而是把 workspace 作为安全边界，并在写前备份。这样 Agent 有修改能力，但不会默认拥有整个机器的文件访问权。

**Likely Follow-ups:** 符号链接怎么处理？备份目录会不会无限增长？为什么备份不等于 checkpoint？

## D04. Shell 工具使用 argv + 策略校验

**Capability:** Tool Runtime / Command Safety

**Code Location:** `codeteam/tools/shell.py`, `tests/test_shell_tool.py`, `code_review/week1_review.md`

**Function:** 用 `argv` 列表和 `shell=False` 执行命令，并限制 cwd、env、timeout、输出大小和危险命令。

**Problem:** Agent 需要运行测试和检查命令，但 shell 是高风险入口：命令注入、删除文件、读外部路径、网络访问都可能发生。

**Design:** Shell 工具不接受一整段 shell 字符串，而是接受参数列表；执行时使用 `shell=False`，捕获 stdout/stderr，设置 timeout 和输出截断，并对危险命令做策略拒绝。

**Invariant:** Shell 工具的执行入口必须是结构化 argv，不能把用户输入拼进 shell 字符串。

**Why This Way:** 这是命令执行安全的基本工程底线。即使还没有 Docker，也要先避免最常见的 shell injection 风险。

**Alternatives:** 直接 `subprocess.run(command, shell=True)` 开发最快，但风险最高；完整 sandbox 最安全，但需要更多基础设施。当前方案是中间层：先把命令形状收窄，再逐步增加审批和 sandbox。

**Verification:** 测试覆盖正常命令、危险命令拒绝、超时、输出截断、cwd 限制等。

**Industrial Reference:** Codex 文档把 sandbox 和 approval policy 分开配置，常见模式包括 `read-only`、`workspace-write`、`danger-full-access`，并通过审批处理越界操作。Cline 也强调读写文件、运行命令都需要显式批准。

**Limitations:** Shell 工具本身仍只是应用层执行封装，不等价于 OS sandbox。早期 review 发现的 `sh -c`、`bash -c`、`python -c` 绕过已经在 Week3 通过 CommandPolicy / SafeExecutor / Docker sandbox 链路补上，但后续必须确保所有生产命令入口都走统一安全链。

**Future Improvement:** 阻止 shell/interpreter `-c` / `-e` 形式，建立 allowlist 或 command policy，并最终接入 Docker / OS sandbox。

**Interview Version:** 我没有让 Agent 直接执行 shell 字符串，而是要求 argv、`shell=False`、timeout 和输出限制。后来我把早期发现的 interpreter `-c` 绕过升级进 CommandPolicy 和 Docker sandbox，形成“应用层执行封装 + policy + sandbox”的分层安全链。

**Likely Follow-ups:** 为什么 `shell=False` 还不够？哪些命令需要审批？怎么做命令风险分类？如何证明 sandbox 没被绕过？

## D05. Agent Loop 的预算、重复动作和无进展停止

**Capability:** Agent Harness / Runtime Reliability

**Code Location:** `codeteam/agent_loop.py`, `codeteam/state.py`, `codeteam/limits.py`, `tests/test_agent_loop_limits.py`, `tests/test_agent_loop_repeated_action.py`, `tests/test_agent_loop_stop_conditions.py`

**Function:** 实现模型调用、工具执行、消息追加和停止条件组成的 Agent 主循环。

**Problem:** 没有停止条件的 Agent 容易无限循环、重复调用同一个工具、或在模型没有给出工具调用/最终输出时卡住。

**Design:** `AgentLoopState` 记录 step count、tool call count 和工具调用指纹；`limits.py` 负责预算检查；主循环统一返回 `AgentLoopResult` 和 `StopReason`。

**Invariant:** Agent Loop 必须在最大步数、最大工具调用、重复动作、无进展、无效输出等情况下明确停止，而不是无限运行。

**Why This Way:** Agent Runtime 的可靠性首先来自可终止性。停止原因结构化后，tester / reviewer 才能定位失败属于哪一类。

**Alternatives:** 把循环写成 while True + break 最快，但 stop reason 会散落在代码里；把状态集中成 `AgentLoopState` 更清楚，也便于测试。

**Verification:** 测试覆盖最大步数、最大工具调用、重复工具调用、没有进展、无效 final output 等路径。

**Industrial Reference:** 长任务 coding agent 都需要预算和停止机制，否则成本、时间和副作用无法控制。OpenAI API 文档也把 background mode、conversation state、tool outputs 等视为运行状态的一部分；CodeTeam 在本地实现了教学版 loop state。

**Limitations:** 当前 loop 和 Week2 context engine 还没有完全接成端到端 coding agent；没有复杂 planner / reflection / retry task graph。

**Future Improvement:** 接入 context build、patch runtime、test runner，把 stop reason 扩展到真实任务级状态。

**Interview Version:** 我把 Agent Loop 做成可终止的 runtime，而不是无限聊天。每次模型响应要么转成工具调用，要么转成通过语义校验的 final output，否则就给出明确停止原因。

**Likely Follow-ups:** 重复动作怎么定义？最大步数怎么设置？遇到工具失败是停止还是继续？如何避免误杀有效重试？

## D06. 事件日志、用量统计和错误分类

**Capability:** Observability / Runtime Reliability

**Code Location:** `codeteam/events.py`, `codeteam/usage/pricing.py`, `codeteam/usage/tracker.py`, `codeteam/errors.py`, `codeteam/llm/openai_compatible.py`, `tests/test_events.py`, `tests/test_usage_tracker.py`, `tests/test_pricing.py`, `tests/test_error_classification.py`, `tests/test_retry.py`

**Function:** 记录模型请求、模型响应、工具调用、停止事件、token 用量、成本和错误类别。

**Problem:** Agent 失败时，如果只有最终一句“失败了”，无法知道是模型输出错、工具错、预算耗尽、还是网络/API 可重试错误。

**Design:** 用 `AgentEvent` 记录关键生命周期事件；`UsageTracker` 逐步累计 token 和成本；`ErrorCategory` 和 retry 配置把不同异常分到可重试/不可重试类别。

**Invariant:** 重要 runtime 行为必须留下结构化证据：发生了什么、在哪一步、用了多少 token、为什么停止。

**Why This Way:** Observability 不是后期锦上添花，而是 Agent Runtime 能被调试、评测和面试讲清楚的基础。

**Alternatives:** 打印日志最简单，但无法机器分析；完整 OpenTelemetry 更工业级，但早期过重。当前结构化事件是轻量可扩展方案。

**Verification:** 单元测试覆盖事件创建、用量累计、价格计算、错误分类和重试策略。

**Industrial Reference:** Cline 企业能力中公开提到 Observability 集成；Claude Code 和 Codex 也都围绕命令、工具、审批、diff、任务状态提供可观察界面。CodeTeam 当前实现的是底层事件模型。

**Limitations:** 还没有 trace id 跨模块串联，也没有持久化日志、可视化面板或 OpenTelemetry exporter。

**Future Improvement:** 给一次 agent run 分配 run_id，把 context、tool、patch、test、eval 事件统一串起来。

**Interview Version:** 我给 Agent Loop 加了事件和用量统计，所以失败不是黑盒。能看到模型哪一步返回了什么、工具调用用了多少次、token 成本是多少、为什么停止。

**Likely Follow-ups:** 事件字段如何设计？日志和 trace 有什么区别？如何避免日志泄露用户代码？成本统计怎么校准？

## D07. RepositorySnapshot 统一仓库事实层

**Capability:** Context Engineering / Repository Scanner

**Code Location:** `codeteam/repository/scanner.py`, `codeteam/repository/models.py`, `codeteam/repository/git_inventory.py`, `codeteam/repository/file_classifier.py`, `codeteam/repository/tree_renderer.py`, `tests/repository/`

**Function:** 扫描 Git 仓库，得到 tracked/untracked 文件、语言、文件角色、重要配置、忽略文件和紧凑目录树。

**Problem:** Coding Agent 不能一上来把整个仓库塞给模型，需要先知道“仓库里有什么、哪些文件重要、哪些应该忽略”。

**Design:** `RepositorySnapshot` 作为统一事实层，其他模块不直接重复扫文件系统，而是消费 snapshot 中的文件清单、语言、角色和配置。

**Invariant:** 后续 context / search / eval 使用同一份仓库事实，避免每个模块各自猜测项目结构。

**Why This Way:** Context Engineering 的第一步不是检索，而是建立稳定的仓库地图。

**Alternatives:** 直接 `os.walk()` 简单，但无法理解 Git 状态和 ignore；每个模块自己扫会造成重复和不一致。统一 snapshot 更适合作为基础设施。

**Verification:** 测试覆盖 Git inventory、文件分类、scanner、tree renderer。

**Industrial Reference:** Claude Code 文档强调能理解整个 codebase；Codex / Cline 都需要项目级上下文和规则加载。CodeTeam 把这件事拆成显式 scanner，方便验证和解释。

**Limitations:** 当前主要面向 Python 仓库，跨语言角色识别还不够丰富。

**Future Improvement:** 增加 monorepo package 边界、构建系统识别、依赖锁文件摘要和大仓库增量 cache。

**Interview Version:** 我没有直接把文件丢给模型，而是先构建 RepositorySnapshot。它把 Git 状态、语言、文件角色和目录树统一成一份事实层，后续检索和上下文构建都基于它。

**Likely Follow-ups:** 为什么需要 Git inventory？如何处理 ignored 文件？大仓库扫描怎么优化？snapshot 会不会过期？

## D08. 统一 ParseResult + AST / Tree-sitter 双解析器

**Capability:** Context Engineering / Parsing

**Code Location:** `codeteam/parsing/models.py`, `codeteam/parsing/base.py`, `codeteam/parsing/python_ast_parser.py`, `codeteam/parsing/tree_sitter_parser.py`, `codeteam/parsing/registry.py`, `tests/parsing/`

**Function:** 定义统一解析结果模型，并支持 Python AST 严格解析与 Tree-sitter 容错解析。

**Problem:** 代码文件可能语法完整，也可能处于用户正在编辑的半坏状态。只依赖 AST 会在语法错误时完全失败；只依赖容错解析又可能丢失 Python 语义精度。

**Design:** `ParseResult` 统一表达成功、失败、诊断和位置；解析器通过 `CodeParser` Protocol 接入 registry；Python AST 用于精确语义，Tree-sitter 用于容错结构。

**Invariant:** 解析失败也是结构化结果，不能变成静默异常；调用方始终面对统一接口。

**Why This Way:** Coding Agent 面对的是 working tree，不是永远可运行的 release snapshot。解析系统必须能在坏代码上降级。

**Alternatives:** 只用 `ast.parse` 简单精确但脆弱；只用 Tree-sitter 跨语言强但语义提取成本更高。双引擎设计保留两边优势。

**Verification:** 测试覆盖解析成功、语法错误、registry 行为和诊断。

**Industrial Reference:** 工业代码智能系统通常会结合文本搜索、语法树、语言服务或增量 parser。CodeTeam 选择 AST + Tree-sitter，是一个可解释的简化版本。

**Limitations:** 当前 Tree-sitter 查询和跨语言支持还很薄，主要服务 Python。

**Future Improvement:** 为 TypeScript / JavaScript 增加 parser，记录 parser version 到 eval manifest，支持增量解析。

**Interview Version:** 我把解析结果统一成 `ParseResult`，并同时支持 AST 和 Tree-sitter。AST 精确但怕坏代码，Tree-sitter 容错但语义弱；双引擎让 Agent 在真实 working tree 里更稳。

**Likely Follow-ups:** AST 和 Tree-sitter 如何选择？语法错误时下游怎么办？为什么需要 Protocol？位置对象有什么用？

## D16. PatchValidator 先校验再应用

**Capability:** Workspace & Sandbox / Patch Runtime

**Code Location:** `codeteam/git/patch.py`, `codeteam/git/workspace.py`, `tests/git/test_patch_validator.py`, `tests/git/test_path_security.py`, `tests/git/test_apply_patch.py`

**Function:** 在真正修改磁盘前，对 patch 做大小、文件数量、binary patch、路径安全、rename/copy path 和 `git apply --check` 校验。

**Problem:** LLM 生成的 patch 可能路径逃逸、修改 `.git`、包含 binary patch、上下文不匹配，或者一次 touching 太多文件。如果直接 apply，会污染用户工作区。

**Design:** `PatchValidator.validate()` 先计算 patch hash，再提取 affected paths；`validate_patch_path()` 拒绝绝对路径、Windows drive、`..` escape、`.git` metadata 和 symlink escape；最后用 `git apply --check` 做 Git 级可应用性检查。

**Invariant:** `check_patch()` 永远不修改 workspace；不安全 patch 必须在写磁盘前被拒绝。

**Why This Way:** Patch 是 Agent 修改代码的标准载体，但 patch 本身不是可信输入。必须把“模型提出修改”和“Runtime 接受修改”分离。

**Alternatives:** 直接调用 `git apply` 快，但安全和失败诊断差；自己解析 unified diff 复杂且容易漏 Git 语义。当前方案复用 Git 解析，同时补充路径安全策略。

**Verification:** 测试覆盖空 patch、binary patch、大小限制、文件数量限制、路径逃逸、绝对路径、`.git` 修改、symlink escape、rename path。

**Industrial Reference:** OpenAI `apply_patch` 工具文档要求 patch harness 解释操作、应用补丁、记录状态并把结果回传模型；CodeTeam 在本地实现了更显式的 preflight validator。

**Limitations:** 目前只支持文本 patch，拒绝 binary patch；复杂 rename/copy、权限变化、文件模式变化还可继续加强。

**Future Improvement:** 增加 patch policy：允许/禁止路径 glob、最大 hunk 数、敏感文件审批、diff preview 给 reviewer。

**Interview Version:** 我没有让 LLM 生成 patch 后直接应用，而是先做 PatchValidator。它检查路径、大小、文件数量、binary patch，并用 `git apply --check` 做预检，保证不安全或不可应用的 patch 不会碰磁盘。

**Likely Follow-ups:** 为什么不用 `git apply --unsafe-paths`？rename 路径怎么提取？symlink escape 怎么防？为什么拒绝 binary patch？

## D17. GitWorkspace 失败无半截副作用

**Capability:** Workspace & Sandbox / Recovery

**Code Location:** `codeteam/git/workspace.py`, `codeteam/git/diff.py`, `tests/git/test_apply_patch.py`, `tests/git/test_diff.py`

**Function:** 封装 Git diff、changed files 和 patch apply，并在 apply 失败时检查 affected files 的 hash 和 Git status 是否保持不变。

**Problem:** Patch 应用最怕“第一部分成功、第二部分失败”，留下半截修改。Agent 接下来会基于污染状态继续行动，错误会级联。

**Design:** `GitWorkspace.apply_patch()` 必须先调用 `check_patch()`；真正 apply 前对 affected paths 做 sha256 snapshot；失败或 timeout 后调用 `_verify_failed_apply()` 比较 before/after，发现半截副作用就抛出 critical error。

**Invariant:** patch apply 要么成功并返回 `APPLIED`，要么失败且 workspace 状态不变。

**Why This Way:** 这是安全编辑链路的原子性设计。即使 Git 正常情况下很可靠，Runtime 也要把“失败不污染”作为显式契约和测试目标。

**Alternatives:** 只相信 `git apply --check` 可通过，但存在并发修改和竞态；直接失败返回错误但不验状态，无法发现部分副作用。snapshot 验证多一点成本，但换来强诊断。

**Verification:** 测试覆盖 wrong context、多个 hunk 中一个无效、失败后文件 hash 和 git status 不变；diff 测试覆盖 staged / unstaged / untracked / rename。

**Industrial Reference:** Cline checkpoint 文档强调每次工具使用后保存快照，可回滚文件状态；CodeTeam 当前还没完整 checkpoint，但已经在 patch apply 层实现了失败无副作用契约。

**Limitations:** snapshot 只覆盖 validator 提取的 affected paths；对非常大的文件和大量文件会有成本。

**Future Improvement:** 和 CheckpointManager 结合，对整个 workspace 或 dirty set 做恢复；记录 before/after diff 到事件日志。

**Interview Version:** 我把 patch apply 做成接近事务的语义：先校验，再 snapshot affected files，失败后验证文件 hash 和 git status 没变。这样可以证明失败不会留下半截修改。

**Likely Follow-ups:** `git apply --check` 和真正 apply 之间有竞态怎么办？为什么只 hash affected paths？untracked 文件怎么处理？critical error 该怎么恢复？

## D18. WorktreeManager 的任务级隔离

**Capability:** Workspace & Sandbox / Multi-Agent Orchestration

**Code Location:** `codeteam/git/worktree.py`, `codeteam/git/models.py`, `tests/git/test_worktree.py`, `test_log/2026-08-12_week3_day2_worktree_test_log.md`

**Function:** 为每个 task 创建独立 Git linked worktree 和独立 task branch，保证多个任务并行修改时不污染 main working tree 或彼此工作区。

**Problem:** 多个 Agent 在同一个目录并行改代码，会互相覆盖文件、切换分支、污染 diff 和测试结果。没有任务隔离，就很难做 multi-agent。

**Design:** `WorktreeManager.create(task_id, base_ref)` 校验 task id，生成 `codeteam/{task_id}` branch 和独立 path；创建前检查 branch/path 冲突；创建后验证当前 branch 和 HEAD sha 等 postconditions。

**Invariant:** 一个 task 的文件修改不能影响 main worktree，也不能影响其他 task worktree。

**Why This Way:** Git 负责版本状态，worktree 负责任务隔离。这个边界比复制整个 repo 更轻，又比共享 working tree 安全。

**Alternatives:** 所有任务共享一个 working tree 最简单但污染严重；clone per task 隔离强但慢且占磁盘；Docker workspace 更强但成本更高。Git worktree 是本地 coding agent 的合理中间方案。

**Verification:** 测试覆盖结构化 `WorktreeInfo`、指定 base_ref、main 不污染、task 间不污染、重复 task id、已有 branch、已有 path、非法 task id、missing base ref 和 subprocess 安全形状。

**Industrial Reference:** Codex 文档公开说明 worktree 可为同一仓库创建第二个 checkout、各自有文件副本但共享 Git metadata；Codex managed worktree 通常绑定单个 chat，并用于后台工作。Cline Kanban 也公开提到 per-card worktrees、auto-commit 和依赖链。

**Limitations:** 当前只实现 create，没有 remove / cleanup / dirty protection / handoff / benchmark；和 Codex 默认 detached HEAD 不同，CodeTeam 当前创建 task branch，便于学习 branch 生命周期。

**Future Improvement:** 增加 cleanup、dirty worktree 拒绝删除、worktree benchmark（create latency、disk usage、P95）、clone-per-task ablation、checkpoint restore。

**Interview Version:** 我用 Git worktree 做 task isolation。每个任务有独立目录和分支，修改不会污染 main，也不会污染其他任务。相比 clone per task 更轻，相比共享目录更安全。

**Likely Follow-ups:** 为什么 Codex 可以 detached HEAD，你这里用 branch？分支已被其他 worktree checkout 怎么办？worktree 怎么清理？和 Docker sandbox 有什么区别？

## D19. CheckpointManager 用 Git 对象保存可恢复状态

## D21. SafeExecutor 阻止 DENY 到达 Runner

**Capability:** Execution Safety

**Code Location:** `codeteam/execution/safe_executor.py`, `codeteam/execution/safe_execution_service.py`, `tests/execution/`

**Function:** 把 policy、approval 和 runner 串成单一执行入口，确保 `DENY` 不会传到底层 runner。

**Interview Version:** 我不是只在 UI 上提示危险，而是在执行服务层保证 DENY 命令根本不会到 runner。这样测试可以断言 backend invocation 为 0。

## D22. Docker Sandbox 做真实能力边界

**Capability:** Sandbox / Security

**Code Location:** `codeteam/sandbox/docker_builder.py`, `codeteam/sandbox/docker_runner.py`, `tests/sandbox/`

**Function:** 为命令执行提供真实容器边界：workspace mount、无网络、只读 rootfs、drop capabilities、no-new-privileges、资源限制。

**Problem:** 应用层路径检查不是 OS 级隔离。恶意或错误命令如果能直接跑在 host 上，仍可能读 secret、联网或写系统路径。

**Invariant:** 容器能读写挂载 workspace，但不能读取未挂载 host secret，不能联网，不能写 root filesystem，不能访问 Docker socket。

**Verification:** 普通环境下 builder 单测通过；提升权限终端下真实 Docker integration `42 passed`。

**Limitations:** 依赖本机 Docker/Colima 权限和本地 `codeteam-sandbox:latest` image；不同 OS 的 mount path 需要持续回归。

**Interview Version:** CommandPolicy 解决“是否允许”，Docker sandbox 解决“即使允许也只能在边界内做”。我用真实 integration test 证明 workspace 可读写、host secret 不可读、网络失败、rootfs 不可写。

## D25. Context Compaction 必须验证压缩后预算

**Capability:** Context Runtime

## D30. TaskDAG 作为 Scheduler 输入而不是线性 Plan

**Capability:** Multi-Agent Orchestration / Task DAG / Dependency Resolution

**Code Location:** `codeteam/agent_team/dag.py`, `tests/agent_team/test_dag.py`, `docs/design_decisions/DD-W5-02.md`, `docs/benchmark/W5_DAG_BENCHMARK.md`, `docs/failure_cases/W5_DAG_FAILURE.md`, `evals/week5/benchmark_task_dag.py`

**Function:** 把 `LeadPlanningResult.assignments` 转成可验证、可拓扑排序、可查询 ready tasks 的 `TaskDAG`。

**Interview Version:** 我把 Lead 的 assignment 转成显式 DAG，而不是把 Plan list 直接交给 Worker。这样 Scheduler 可以用图结构判断哪些任务可运行，并在执行前发现 cycle 或 missing dependency。

## D31. 同步状态机 Scheduler 和原子 task claim

**Capability:** Multi-Agent Orchestration / Scheduling / Ownership / Concurrency Control

**Code Location:** `codeteam/agent_team/scheduler.py`, `codeteam/agent_team/dag.py`, `codeteam/agent_team/worker.py`, `codeteam/events.py`, `tests/agent_team/test_scheduler.py`, `docs/design_decisions/DD-W5-03.md`, `docs/benchmark/W5_SCHEDULER.md`, `docs/failure_cases/W5_SCHEDULER_FAILURE.md`, `evals/week5/benchmark_scheduler.py`

**Function:** 把 DAG dependency-ready 节点幂等入队，并通过同步状态机完成 `READY -> CLAIMED -> RUNNING -> COMPLETED/FAILED`。

**Problem:** `asyncio.gather()` 或普通队列无法证明唯一 ownership、owner-only complete/fail、bounded retry 和并发 claim 下无重复执行。

**Design:** `TaskScheduler` 使用 `threading.Lock + deque + queued_node_ids`。`TaskRuntimeRecord.status` 是 Scheduler runtime 状态权威；`WorkerAssignment` 保持 planning contract；`WorkerAgent.info` 返回防御性快照。claim 在同一临界区检查 worker availability、role compatibility、task status、queue membership，并写入 owner。

Day3 hardening 后，Scheduler 构造时先调用 `TaskDAG.validate()`，再复制 DAG topology，且只接受全 `PENDING` fresh DAG；构造后不读取原 DAG status 或动态 topology mutation。公共 `TASK_TRANSITIONS` 是不可变 mapping。事件提交与外部 `event_sink` 投递分离：内部状态和审计事件在锁内提交，sink 在锁外接收防御性副本，sink 普通异常被隔离并记录为 `scheduler.event_delivery_failed`。缺少兼容 role 的 Worker 时，任务保持 `PENDING` 并返回 `waiting_for_worker`，不再误标为 terminal `BLOCKED`。

**Invariant:** 同一个 `node_id` 同一时刻只能有一个 `owner_id`；非 owner 不能 start/complete/fail；terminal state 不可回退；retry 受 `max_attempts` 限制。

**Verification:** Tests 覆盖 schedule 幂等、role mismatch、busy/stopped/failed worker、两个线程竞争一个 task、多 worker 多 task 无重复、owner-only complete/fail、非法状态推进、retry 上限、Scheduler 事件、event sink 重入/异常隔离、不可变 transition、missing role recovery、fresh DAG 初始化拒绝、未 validate 环形 DAG 拒绝和有界线程 join。Benchmark 分开记录 scheduler setup latency、schedule-only latency、claim throughput、contention failure rate，并记录 base HEAD、dirty state、Python、seed、文件 SHA-256。

**Limitations:** 当前只证明进程内线程级原子性；不证明跨进程/分布式锁、Worker crash recovery、heartbeat、durable queue、Mailbox 或端到端 Multi-Agent 加速。

**Interview Version:** 我没有把多个 Worker 简单 `gather` 起来，而是设计了同步状态机 Scheduler。任务先由 DAG 判断 dependency-ready，再幂等进入 ready queue；Worker claim 时在锁内完成状态 CAS、owner 写入和 queue membership 更新，所以并发竞争只有一个 Worker 成功。

## D32. 进程内 Mailbox 而不是 Agent 直接调用

**Capability:** Multi-Agent Orchestration / Agent Communication / Observability

**Code Location:** `codeteam/agent_team/mailbox.py`, `codeteam/agent_team/__init__.py`, `codeteam/events.py`, `tests/agent_team/test_mailbox.py`, `docs/design_decisions/DD-W5-04.md`, `docs/benchmark/W5_MAILBOX.md`, `docs/failure_cases/W5_MAILBOX_FAILURE.md`, `evals/week5/benchmark_mailbox.py`

**Function:** 为 Lead 和 Worker 提供进程内结构化通信层。每个注册 agent 有自己的 inbox，发送方通过 `AgentMessage` 放入收件箱，接收方用非阻塞 `receive()` destructive 消费。

**Problem:** 直接函数调用会把 sender 和 receiver 生命周期绑死，也无法表达 receiver 暂时未处理、队列积压、容量、审计、安全 metadata 和广播原子性。

**Design:** `AgentMailbox` 使用 `threading.Lock + deque`。Mailbox 有独立地址簿，不复用 `WorkerRegistry`；Lead 和 Worker 都能注册，`AgentStatus.BUSY` 不影响收件。`send()` 校验 sender/recipient、重复 `message_id` 和容量；`broadcast()` 使用显式 recipient list，为每个 recipient 生成独立 message_id，共享 correlation_id，并在同一锁内 all-or-nothing 入队。事件只记录安全 metadata，event sink 在锁外投递，sink 普通异常被隔离并记录为 `mailbox.event_delivery_failed`。

**Invariant:** `AgentMessage` 是待消费通信载体，不是 `AgentEvent`，也不是 `codeteam.schemas.messages.Message`。Mailbox 消息不能直接推进 Scheduler 状态；`TASK_COMPLETED` message 只能触发后续逻辑，真正完成任务仍必须调用 `TaskScheduler.complete()` 并通过 owner/status 检查。

**Verification:** Tests 覆盖模型校验、Lead/Worker 地址注册、未知 sender/recipient、重复 agent、点对点收发、空 inbox、per-inbox FIFO、重复 message_id、payload 防御性副本、容量满、broadcast 原子性、并发 producer 无丢失无重复、安全审计字段、event sink 重入/异常隔离和公共 API 导出。Benchmark 覆盖 100/1000/10000 消息、1/4/8 producers、broadcast fan-out、setup/send/receive 热路径和近似 backlog bytes。

**Limitations:** 当前只证明进程内、非持久化、每 inbox FIFO、destructive receive、at-most-once dequeue。它不证明 heartbeat、worker crash recovery、ack/nack、durable replay、SQLite mailbox、exactly-once、cross-process delivery 或端到端 Multi-Agent 加速。

**Interview Version:** 我没有让 Worker 直接调用 Lead，而是加了一层结构化 Mailbox。消息进入每个 Agent 的 inbox，发送和接收被线程锁保护，并记录安全审计事件；但消息本身不会绕过 Scheduler ownership。第一版刻意保持进程内和非持久化，先证明通信正确性，再把 crash recovery 和 durable replay 留给后续模块。
