# DD-W4-D7-08: Verification Environment Contract Before Provider Execution

Status: Accepted
Date: 2026-08-29

## Problem

The Runtime required verification commands that its Docker environment was not
guaranteed to support. A user-run B01 produced the correct source patch through
native tools, but `python -m pytest ...` failed inside the configured image with
`No module named pytest`. The existing Docker preflight had only proved that the
CLI, daemon, image, bind mount, and container startup worked.

The failed command was then treated as a test assertion failure. The model tried
the repository-recommended `uv run pytest`, the exact task verification contract
rejected that substitution, and retrying the authoritative command eventually
became `repeated_action`. The repeated action was a secondary symptom.

## Alternatives

### A. Let the Agent discover and repair the missing dependency

Rejected. It spends Provider tokens on a fact the Runtime can know in advance,
asks the Agent to repair infrastructure outside its source workspace, and
pollutes task-failure metrics.

### B. Allow automatic substitution with `uv run pytest`

Deferred. It weakens the authoritative task command and still does not prove
that `uv` exists in the container.

### C. Mount the host `.venv`

Rejected. A macOS host environment is not a Linux-container runtime contract;
mounting it weakens isolation, ABI portability, and reproducibility.

### D. Separate verification preflight and pin a project-owned toolchain

Accepted. The project owns a minimal Python 3.11 image with exact pytest and
transitive dependency versions. A second fixed, Runtime-owned probe checks
Python and pytest before any Provider call.

## Decision

Keep `DockerSandboxPreflight` as the infrastructure check and introduce
`DockerVerificationEnvironmentPreflight` for the logical Python+pytest
verification contract.

```text
Sandbox Infrastructure Preflight
  -> test -d /workspace
  -> Docker/image/mount/container availability

Verification Environment Preflight
  -> python --version
  -> python -m pytest --version
  -> image ID/digest and tool versions

Task Verification
  -> authoritative task argv through SafeExecutionService
  -> test assertion evidence
```

The project image is built from `docker/sandbox/` only. Its Python base is
pinned by exact tag and digest; pytest and its direct runtime dependencies are
exactly pinned. Runtime execution never performs `pip install`, pulls an image,
or mounts the host `.venv`.

## Invariants

- Sandbox availability is not verification environment readiness.
- A missing Python/pytest toolchain stops before Provider execution: steps,
  tool calls, tokens, cost, and repair attempts remain zero.
- A toolchain failure is `verification_environment_failed`, not a test
  assertion failure and not `repeated_action`.
- A normal pytest assertion failure remains Agent-visible task feedback.
- Preflight probes are fixed infrastructure argv; they do not pass through or
  relax model-facing `CommandPolicy` rules.
- Agent `run_tests` still uses the exact visible allowlist and
  `SafeExecutionService`.
- Runtime and verification preflight use the same configured image profile.
- Runtime Docker Python and trusted-host Grader Python may be physically
  different, but manifest evidence records their shared logical capabilities
  and versions.

## Trade-offs

The Runtime now performs two short container probes and one local image inspect
before the first Provider call. This adds startup latency, but prevents a much
more expensive model/repair loop on an incapable environment.

The current requirement detector intentionally supports only the Week4
`python -m pytest` contract. Unsupported authoritative commands fail closed;
this is narrower than a general multi-language environment manager.

## Verification

- Unit tests cover ready, missing Python, missing pytest, unsupported command,
  assertion failure classification, fixed probe metadata, and image contract.
- Runtime integration tests prove Provider invocation count zero on preflight
  failure, no repair/repeated-action evolution, and terminal handling if the
  toolchain disappears after preflight.
- The final digest-pinned image was built locally without a Provider call.
- Real Docker Sandbox tests verify image metadata, Python 3.11.15, pytest 9.1.1,
  workspace isolation, no network, read-only rootfs, and no Docker socket.

Post-change B01 is `NOT_RUN_BY_CODER`; user validation remains pending.
The 11-task benchmark and ablation are `NOT_RUN`.

## Limitations

- This contract guarantees Python and pytest only. It does not infer arbitrary
  task dependencies or provision Node, Java, Rust, `uv`, or repository-specific
  packages.
- A repository that needs additional Python dependencies must declare a future
  explicit environment contract; dynamic provisioning is intentionally absent.
- Preflight cannot eliminate toolchain failure after the probe, so `run_tests`
  retains a narrow runtime classifier for executable/module disappearance.
- Completion Ownership / `READY_TO_FINALIZE` remains pending and unchanged.

## Interview Version

The Agent had already generated the correct patch, but Docker lacked pytest.
Our old preflight only answered “can the container start?”, so the Runtime spent
model tokens treating infrastructure as a code failure until repeated-action
stopped it. I separated sandbox readiness from verification readiness, pinned a
minimal project image, added fixed Python/pytest probes before the Provider, and
kept real test execution behind the existing SafeExecution boundary.
