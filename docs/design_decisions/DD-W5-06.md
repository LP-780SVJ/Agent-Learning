# DD-W5-06: Durable Team State and Process Resume

## Status

FUNCTIONALLY_ACCEPTED; weekend benchmark and ablation pending.

## Evidence Status

Correctness: deterministic unit, integration, concurrency and selected real
`os._exit` process-crash tests implemented. Performance and ablation evidence:
WEEKEND_PLANNED / NOT_RUN. This decision does not claim cross-machine recovery,
external side-effect exactly-once, or complete recovery from every SIGKILL point.

## Context

Day5 handles Worker loss while one Python Runtime still owns its in-memory
`TeamStateCoordinator`. A process exit destroys the coordinator, locks, monotonic
deadlines, Worker objects and claims. Loading Session JSON alone cannot reconstruct
the Team DAG, queue, ownership, Mailbox or restart budget.

Three authorities must remain distinct:

- `JsonSessionStore`: Session lifecycle, repository/worktree/checkpoint and the
  top-level resume writer lock.
- `SQLiteTeamStateStore`: Team DAG, Task runtime, Worker durable metadata, queue,
  Mailbox delivery state and Team events.
- Git/Checkpoint: actual source-code effects and recovery evidence.

Session JSON and Team SQLite cannot share one database transaction. Recovery must
therefore tolerate and reconcile explicit revision gaps instead of claiming
cross-file atomicity.

## Decision

Use a normalized per-Session SQLite database named `team_state.sqlite3`, stored
inside the protected Session directory. Task, dependency, Worker, queue, ownership,
Mailbox and event records have dedicated tables. SQLite runs in WAL mode with
foreign keys, `synchronous=FULL`, explicit schema versioning and owner-only file
permissions. A symlink Session directory is rejected.

`TeamStateSnapshot` is the public durable contract. Registry, Scheduler and
Mailbox expose package-owned snapshot/hydration methods; the Store never reads
their private dictionaries. Locks, callbacks, connections, `WorkerAgent`, old
`WorkerLease`, old `TaskClaim` and monotonic heartbeat values are excluded.

Every Team mutation uses `expected_revision` CAS. State rows and Team event rows
commit in one SQLite transaction. Observer sinks are not a durability mechanism.
The DB revision and event sequence are allocated by the Store.

Mailbox delivery uses `PENDING -> IN_FLIGHT -> ACK` with a durable claim id,
runtime id and delivery attempt. A matching claim may be released to PENDING.
Deduplication history remains after ACK. Claim is committed before the message is
returned, avoiding the previous pop-then-persist lost-message window. This is
at-least-once control-plane delivery, not external exactly-once execution.

Resume always creates a new `TeamStateCoordinator` and runtime_id. Reconciliation
preserves task attempt, Worker generation history, restart attempts, ready/waiting
membership and message order, but discards old runtime authorization. Active
Worker generations advance; STOPPED Workers stay stopped. UTC restart deadlines
are durable and are converted to a fresh monotonic deadline at hydration time.
Old runtime leases, task claims and message claims are rejected.

CLAIMED/RUNNING Tasks never continue blindly. With no unresolved Git/operation
evidence, they re-enter READY only while retry budget remains; otherwise they fail
and terminal dependency blocking propagates. Unknown Git effects or an active
started Session operation produce `RECOVERY_REQUIRED` without rewriting the Team
snapshot into a false success.

The publication order is fixed:

```text
Session writer lock
-> load Session + Team state
-> Session/Git reconciliation
-> prepare and CAS-commit Team state/event for new runtime_id
-> hydrate fresh runtime objects
-> save Session RUNNING with acknowledged Team revision
-> append SESSION_RESUMED
```

If the Team commit succeeds but Session save does not, SQLite may be ahead of the
Session hint; the next resume reconciles this bounded gap. A Team DB behind the
Session hint fails closed. Hydration failure is audited when possible and Session
resume becomes `RECOVERY_REQUIRED`.

## Alternatives

| Option | Benefit | Why not selected |
| --- | --- | --- |
| Memory only | Smallest implementation | Cannot survive process exit |
| One JSON snapshot | Easy inspection and atomic replace | Weak fit for concurrent CAS, message claim/ack and state/event transaction |
| Pure event sourcing | Complete replay history | Adds projection, event migration and replay complexity before evidence requires it |
| SQLite JSON blob | Simple Store code | Hides relational invariants and conflicts with immediate Task/Message normalization |
| Normalized SQLite snapshot + event history | Local transaction, CAS and inspectable rows | Selected; schema evolution and write amplification must be managed |
| Remote database/workflow engine | Multi-process/host foundations | Out of scope for local-first V1 |

## Consequences

Recovery is explicit, inspectable and fenced by a new runtime epoch. SQLite gives
atomic Team state/event commits but cannot include Git or Session JSON. The
runtime therefore remains fail-closed and reconciliation-heavy by design.

Normalized replacement writes are currently straightforward rather than
incremental. They may amplify writes at 1000 Tasks; no performance conclusion is
made before the weekend benchmark. WAL can create `-wal`/`-shm` sidecars, so the
entire protected Session directory is part of the storage boundary.

`DurableTeamRuntime` is the supported mutation/persistence gateway. If an in-memory
mutation succeeds but persistence fails, the runtime is poisoned and refuses
further mutation because its state is no longer proven equal to SQLite.

Independent acceptance found that the first implementation still exposed raw
mutable Registry/Scheduler/Mailbox/Lifecycle objects. The hardened runtime now
keeps those objects private and exposes controlled facades: reads return copied
models, while every public mutation routes back through the runtime durability
gate. Nested `scheduler.registry` and `lifecycle.registry/scheduler` references
return facades rather than raw components. `restart_worker` and `sweep` are part
of the same gateway. This is a public API durability contract, not a claim that
Python underscore attributes form a hostile-code sandbox.

A mutation that changes neither business state nor durable events does not commit
a new revision. Volatile capture fields such as `updated_at` and the UTC projection
of a monotonic restart deadline do not manufacture state changes. Audit-only
events still commit a revision.

The Store validates the complete event chain on load and rejects sequence gaps,
session mismatch, invalid/future revision and revision regression. Before every
SQLite open it uses `lstat` to reject symlinks at the database, WAL, SHM and journal
paths. This prevents the demonstrated ordinary symlink escape, but a userspace
check/open TOCTOU window remains; this is not kernel-enforced path confinement.

## Verification

Tests cover model round-trip and invariant rejection; normalized schema and file
permissions; initialize/load/CAS/schema/corruption; state/event rollback; message
claim/ack/release; full DAG/Registry/Scheduler/Mailbox hydration; new runtime id;
old lease/claim rejection; UTC deadline conversion; retry and terminal closure;
Session/Team revision gaps; two-process writer exclusion; `os._exit` inside a
SQLite transaction; Team-commit-before-Session-save recovery; and unknown Git
effects after process exit.

Exact command totals belong in the Day6 test logs. The acceptance hardening suite
proves facade persistence, nested raw-reference closure, no-op semantics, lifecycle
restart/sweep persistence, controlled-file symlink rejection and event/meta drift
rejection. Independent re-review confirmed that four remaining failures came from
an acceptance assertion that required a durable mutation while also requiring the
post-call database to equal its pre-call snapshot. The corrected test now requires
one revision advance and equality between live and newly persisted state; all four
facades pass that contract. Weekend performance/ablation runs remain pending.

## Remaining Limits

- No distributed database, multi-primary runtime or cross-machine scheduling.
- No external command/Git side-effect exactly-once guarantee.
- No proof for arbitrary SIGKILL instruction points.
- No automatic semantic repair of ambiguous Git effects.
- No SQLite online migration beyond explicit version refusal.
- No measured 100/500/1000 Task performance yet.

## Interview Focus

Explain why runtime_id, generation and attempt are separate fences; why SQLite
transactions do not remove the need for Git/Session reconciliation; why durable
Mailbox claim/ack is still at-least-once; and how the DB-ahead crash window is
made recoverable without pretending two stores are one transaction.
