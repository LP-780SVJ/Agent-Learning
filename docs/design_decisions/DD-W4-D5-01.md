# DD-W4-D5-01: Structured Context Compaction

- **日期**: 2026-08-21
- **模块**: `codeteam/context/compaction.py`, `codeteam/context/assembler.py`, `codeteam/agent/orchestrator.py`
- **状态**: Accepted（MVP 实现完成）
- **Evidence status**: PROPOSED（Ablation A3 周度执行后再升级）

---

## Problem

长对话会把模型上下文窗口填满。简单截断最旧消息能省 token，但会丢掉早期用户约束、失败测试、当前计划和 checkpoint，导致 Agent "忘记"任务边界。

更危险的是：如果把 LLM summary 当成唯一事实来源，summary 漏掉约束或错误改写计划状态，Runtime 会把模型生成的二手摘要误当权威状态。

## Context

Week4 Day5 引入会话级 Context Compaction。它不同于 Week2 的代码文件压缩：本模块压的是 Agent 会话历史，目标是把早期交互变成结构化 working memory，同时保留最近窗口。

Day4 已建立 Durable Session：TaskSpec、Plan、Checkpoint、Provider/Model、Usage 等是 durable facts。Day5 的 compaction 必须尊重这条边界。

## Requirements

1. 压缩不得删除 Durable Session History。
2. LLM summary 不能成为 safety / constraints / plan / checkpoint 的权威来源。
3. 用户约束、当前 Plan、当前 Checkpoint 必须从 durable facts 或 authoritative inputs 重新注入。
4. Summary 只描述过去发生的事实、决策、失败尝试、未解决问题。
5. Recent Window 即使单条消息超预算也要保留，并且必须可观测。
6. 压缩结果必须输出 tokens_before / tokens_after / summary_tokens / recent_window_tokens，供 Benchmark/Ablation 使用。

## Alternatives

### Option A: Naive Truncation

- **优点**: 实现最简单；无需 summarizer。
- **缺点**: 不知道删掉了什么；容易删除早期用户约束和失败测试；无法审计。

### Option B: Free-form LLM Summary as Source of Truth

- **优点**: 上下文短；模型阅读自然。
- **缺点**: summary 可能漏报、幻觉、改写状态；安全约束和计划状态会被模型二次生成污染。

### Option C: Structured Summary + Authoritative Re-injection（选定）

- **优点**: 有损摘要只承载 working memory；约束、计划、checkpoint 从权威来源重注入；审计和评测字段明确。
- **缺点**: 需要维护分层组装逻辑；summary schema 比纯文本复杂。

### Option D: Provider-native Compaction

- **优点**: 可能利用 provider 内部优化；集成体验好。
- **缺点**: Provider-specific；不利于本项目证明 provider-neutral runtime；不同 provider 的压缩语义不可比。

## Decision

采用 **Structured Summary + Authoritative Re-injection**。

```text
Durable facts / authoritative inputs
  -> system rules / task constraints / plan / checkpoint

ContextSummary
  -> confirmed facts / decisions / failed attempts / unresolved issues

Recent Window
  -> 最近对话、工具结果、当前局部上下文
```

LLM summary 不是 safety、constraints、plan、checkpoint 的权威来源。它只能帮助模型记住"之前发生过什么"，不能改写 Runtime 的 durable facts。

## Why

1. **安全边界清楚**：用户约束不依赖模型是否记得。
2. **可恢复**：Resume 后可以从 durable session 重建 plan/checkpoint，而不是信任旧 summary。
3. **可审计**：CompactionResult 记录压缩前后 token 与消息引用。
4. **Provider-neutral**：不绑定某一家 provider 的上下文压缩能力。
5. **可做 Ablation**：可比较 No Compaction / Naive Truncation / Structured Compaction。

## Consequences

- `ContextSummary` 必须保持结构化，而不是任意文本。
- `ContextAssembler` 必须把 authoritative sections 放在 summary 之前。
- `_try_compact()` 必须消费 `CompactionResult.tokens_after`；压缩后仍超目标预算时不能继续下一轮模型调用。
- `recent_window_over_budget=True` 必须进事件流，避免 silent degradation。

## When to Revisit

- A3 Ablation 完成后，如果 Structured Compaction 没有降低 lost constraint rate 或 repeated retrieval rate，应重新评估复杂度。
- 如果 provider-native compaction 能暴露可审计、provider-neutral 的结构化结果，可作为后端实现替换，但不能改变 authoritative re-injection 的边界。
