# DD-W5-01: Lead-Worker Architecture Instead of Peer Agents

## Status

Accepted for Week5 Day1 foundation.

## Evidence Status

PROPOSED. Day1 implements and tests the domain contracts only. It does not
claim that Lead-Worker improves task success, latency, cost, or merge quality.

## Context

CodeTeam already has a tested Single-Agent Runtime: task modeling, repository
inspection, planning, safe execution, verification, repair, session state, and
evaluation foundations. Week5 starts the move toward Multi-Agent Orchestration.

The system needs a team-level control plane that can split a user task into
structured work assignments without creating a second task or plan source of
truth.

## Problem

Starting several peer agents is not enough for coding tasks. The runtime still
needs one place to answer:

- What is the current global goal?
- Which plan is authoritative?
- Which worker role should handle each step?
- How are duplicate identities rejected?
- Who is allowed to mark team-level work complete?

Without this boundary, workers can compete for the same files, drift from the
global plan, or produce changes that cannot be attributed.

## Requirements

- Reuse existing `TaskSpec`, `Plan`, `PlanStep`, `Planner`, and
  `RepositoryContext`.
- Do not add worker fields to `PlanStep`.
- Do not create `TeamTask` or `TeamPlan`.
- Keep Lead as a planning and assignment control plane.
- Keep Worker as an identity/role facade on Day1, not an execution engine.
- Keep assignment output structured, validated, serializable, and suitable for
  Day2 DAG construction.
- Preserve Single-Agent as baseline and future worker execution kernel.

## Decision

Use Lead-Worker as the Week5 default architecture.

Day1 adds a small `agent_team` package:

- `AgentRole`, `AgentStatus`, `AgentIdentity`, and `AgentInfo` define worker
  identity and role vocabulary.
- `WorkerAssignment` links an existing `PlanStep` to a recommended worker role.
- `LeadPlanningResult` holds an existing `Plan` plus complete assignments.
- `WorkerAgent` and `WorkerRegistry` provide registration and discovery only.
- `LeadAgent.create_plan()` calls an injected `Planner`, then maps each plan
  step to a `WorkerAssignment`.
- `DeterministicRoleAssigner` provides a fixed, reproducible role assignment
  baseline.

## Alternatives

### A. Continue With Single Agent

Simpler, cheaper, and easier to debug. It remains the baseline for simple
tasks. It does not express worker identity, role assignment, or future
parallelism.

### B. Peer Agents

Useful for review, debate, and independent hypothesis exploration. It is not
the default for CodeTeam because global state, ownership, completion, and
recovery become harder to define.

### C. Lead-Worker

Clear global source of truth and audit boundary. The cost is extra coordination
logic and the risk that the Lead becomes a bottleneck or decomposes poorly.

### D. Static Planner-Executor Workflow

Very deterministic and simple to schedule. It is weaker for future dynamic
replanning, worker lifecycle, and mailbox-based coordination.

## Consequences

- Lead and Worker boundaries are independently testable.
- Assignment is machine-readable instead of free text delegation.
- Day2 can build a DAG from `LeadPlanningResult.assignments`.
- Day3 can schedule workers without changing `PlanStep`.
- Day6 can persist team projections without serializing runtime objects.

The decision also adds coordination overhead and requires future benchmarks to
show when team mode is worth enabling.

## Benchmark Plan

Status: PLANNED / NOT_RUN.

Day1 benchmark is a planning-layer benchmark, not an end-to-end team execution
benchmark.

Questions:

- Does Lead produce non-empty, valid `LeadPlanningResult` objects for complex
  tasks?
- What is role assignment accuracy against a small labeled task-step dataset?
- What is deterministic planning overhead compared with Planner-only output?
- How often does Lead produce empty or inconsistent assignments?

Metrics:

- valid_result_rate
- empty_assignment_rate
- role_accuracy
- role_conflict_rate
- planner_ms and lead_assignment_ms
- serialized_result_bytes

Controls:

- Same `TaskSpec`, `RepositoryContext`, `Planner`, and repository revision.
- Same role gold labels.
- Same Python version and dependency set.
- No worker execution in this benchmark.

## Ablation Plan

Status: PLANNED / NOT_RUN.

Planned ablations:

- Lead-Worker assignment vs peer-agent routing.
- Structured `LeadPlanningResult` vs free-text delegation.
- Role-aware assignment vs all steps assigned to `GENERAL`.
- Deterministic assigner vs future LLM role assigner.

Controls:

- Keep tasks, model/provider, repository context, budget, and safety policy
  fixed.
- Change only one coordination component per ablation.
- Report failures and costs even when role assignment looks plausible.

## Failure Cases

### F-W5-D1-01 Empty Plan

Planner returns `steps=()`, or Lead returns zero assignments. Expected signal:
construction or validation fails; the runtime must not treat this as success.

### F-W5-D1-02 Wrong Role

RoleAssigner maps test work to frontend/backend or security review to general.
Expected signal: role gold-label mismatch in benchmark.

### F-W5-D1-03 Cannot Decompose

Task is too vague or repository evidence is insufficient. Expected signal:
Lead must fail closed in a structured way in later days; it must not fabricate
specific assignments.

### F-W5-D1-04 Duplicate Worker Identity

Two workers register the same `agent_id`. Expected signal:
`DuplicateWorkerError`, and the original worker remains registered.

### F-W5-D1-05 Lead Executes Worker Side Effects

Lead calls patch, shell, workspace, runner, or worker execution from
`create_plan()`. Expected signal: tests fail because Lead exposes or invokes
execution APIs.

## Current Evidence

- Day1 implementation has unit tests for models, Worker registry, Lead
  assignment, deterministic role priority, and Lead execution boundary.
- Existing Week1-4 runtime remains the execution foundation and evaluation
  baseline.

## Evidence Still Missing

- End-to-end Agent Team task success.
- Single-Agent vs Agent Team success/cost/latency comparison.
- Scheduler claim behavior and worktree ownership safety.
- Mailbox information flow and team resume durability.
- Real model role assignment quality.
