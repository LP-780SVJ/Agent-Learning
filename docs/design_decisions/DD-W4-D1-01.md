# DD-W4-D1-01: Structured Execution Plan

- **日期**: 2026-08-09
- **模块**: `codeteam/planning/`
- **状态**: Accepted（实现完成）
- **Evidence status**: PROPOSED

---

## Problem

CodeTeam 如何表示一次多步骤的 Coding 工作？

用户输入 "修复登录超时问题" 后，Runtime 需要回答：

- 当前执行到哪一步？
- 哪一步失败？失败后恢复到哪？
- 计划是否仍然有效？
- 什么时候需要 Replan？
- 怎么向用户展示进度？

如果 Plan 只是一段自然语言散文，这些问题都无法可靠回答。

## Context

Week 1-3 已完成的模块：

- Agent Loop（Week 1）
- Context Engine：RepositoryScanner / SymbolIndex / ImportGraph / Ranking / RepoMap（Week 2）
- Git / Worktree / Checkpoint / CommandPolicy / Sandbox（Week 3）

Week 4 的目标是把这些零件接成 Single-Agent Coding Runtime。Day 1 实现 `codeteam run "任务"` 的生命周期骨架：Natural Language → TaskSpec → Repository Inspection → Plan → READY。

## Requirements

1. Runtime 能追踪每个步骤的执行状态（pending/running/completed/failed/skipped）
2. 新证据推翻假设时能生成新版本 Plan，且保留历史
3. 模型输出必须被 Runtime 验证（空 steps、重复 ID、非法初始状态必须被拒绝）
4. Plan 必须基于 Repository Inspection 的真实证据，而不是模型猜测
5. 后续可持久化、可评测（Step 7 Benchmark 的 step_count / grounding 指标依赖结构化 Plan）

## Alternatives

### Option A: Free-form Natural-Language Plan

```text
首先我会查看登录相关代码，然后检查 timeout，接着修改...
```

- **优点**: 模型容易生成；人类阅读自然；Prompt 简单
- **缺点**: Runtime 无法可靠知道有几步、当前哪一步、哪一步失败、怎么恢复、怎么 Replan、怎么计算 Step Completion

### Option B: Structured Plan / PlanStep

```python
PlanStep(step_id="P1", title="Trace timeout flow",
         status=PENDING, relevant_files=(...), verification="pytest ...")
```

- **优点**: 状态可追踪；可恢复；可 Event Log；可 Replan；可 CLI 展示；可 Evaluation；可 Persist
- **缺点**: Schema 更复杂；模型输出需要验证；可能限制模型表达

## Decision

**Structured Plan 是 Runtime source of truth；natural-language description 保留给人读（title/description 字段）。**

具体落地：

| 元素 | 设计 |
|---|---|
| PlanStep | 稳定 step_id + 执行状态机（PENDING→RUNNING→COMPLETED，禁止 PENDING→COMPLETED 直跳） |
| Plan | steps 用 tuple（序列不可替换）；version 递增（replan 不覆盖历史） |
| 验证 | `validate_plan`（≥1 step、ID 唯一）+ `create_plan` 工厂（初始全 PENDING） |
| Grounding | Planner 输入必须是 RepositoryContext（Week 2 检索证据），Inspection 先于 Planning |
| 状态机 | TaskStatus 9 状态 + 集中转移表 + `transition_to()` 唯一入口 |

## Why

1. **Explicit progress tracking** — 状态可查询，不是从聊天历史推断
2. **Persistence** — 结构化数据可序列化（Day 4 Session Persistence 的基础）
3. **Replanning** — version 字段支持"新证据推翻假设"的演进，不静默覆盖
4. **Validation** — 模型输出必须过 Runtime 闸门，不是"返回什么接受什么"
5. **Observability** — 事件（task.created/plan.created/...）可形成完整 Trace
6. **Evaluation** — 未来评测可计算 step_count、grounding validity 等指标

## Trade-offs

- **Schema complexity**: 比自由文本多了字段约束和校验代码
- **Validation overhead**: 每次 Plan 生成都要过校验（相对收益，成本可忽略）
- **Model output constraints**: 需要 Prompt 契约 + JSON 解析约束模型输出格式

## Consequences

- Planner 接口固定为 `create_plan(task, repo_context) -> Plan`，只有这一个方法——接口层面杜绝 Planner 越权执行
- 非法状态转移在 `transition_to()` 被拒绝，Terminal 状态不可复活
- 坏模型输出（非 JSON / 空 steps / 重复 ID / 非 PENDING 初始状态）在解析层和工厂层被拒绝

## When to Revisit

- **Week 4 末 Ablation 之后**: Plan-first vs Direct-edit 的 Task Success 数据出来后，评估本决策是否 SUPPORTED
- **发现 Structured Plan 限制模型表达时**: 可考虑"结构化 + 自由文本说明"混合字段（当前 title/description 已部分覆盖）
- **Replan 频率过高时**: 增加 ReplanReason 分类与振荡防护
