# DD-W4-D7-11: Progress-aware Agent Execution

## Status

Accepted and implemented offline on `week4`; real-provider stability validation is pending user execution.

## Problem

The 2026-08-29 F03 run used all 20 model turns and 37 tool calls without one
patch. The calls were individually diverse, so repeated-action and cached
no-progress guards did not fire. By turn 19 the model had a viable minimal
implementation idea, but the Runtime offered neither an escalating progress
checkpoint nor a typed terminal outcome for analysis paralysis.

## Alternatives considered

1. Increase `max_steps`: postpones the same failure and increases cost.
2. Treat every read as progress: diverse exploration can reset the clock forever.
3. Prompt-only instruction: gives no runtime policy, typed outcome, or metrics.
4. One soft warning: helps but can still end as undifferentiated `max_steps`.
5. Turn-based soft checkpoints plus terminal pause: selected.

## Decision

`ProgressTracker` separates three facts:

- source progress: a successful `apply_patch` that advances workspace version;
- diagnostic progress: new evidence from focused read/search/test/environment tools;
- completion progress: current-version verification/diff/gate readiness.

At 40% and 70% of the model-turn budget it injects one escalating advisory per
workspace version into the next ordinary `ModelRequest`. This adds no provider
call and consumes no extra step. At 85%, if no source change occurred, both
advisories fired, and completion is not ready, Runtime pauses with
`failure_category=no_source_progress` and diagnostic evidence. A successful
patch resets the per-version advisory state. Diagnostic evidence is counted but
cannot reset source stagnation.

## Invariants

- Runtime never forces a speculative patch.
- `REPEATED_ACTION`, cached `NO_PROGRESS`, `MAX_STEPS`, and completion ownership remain intact.
- Thresholds are model turns, not batched tool-call counts.
- Advisory insertion never makes an extra provider request.
- Resume may rebuild the per-version streak; cumulative metrics and workspace version remain durable.

## Trade-offs and limitations

The policy detects absence of a source transition, not semantic quality. It
cannot prove a patch is correct and must not be described as semantic
understanding. Fixed ratios may need future calibration across model families;
the stability campaign is designed to expose false-positive pauses before that
calibration becomes a benchmark claim.

## Verification

Deterministic tests cover diverse diagnostics, duplicate evidence, advisory
levels, terminal pause, patch reset, completion suppression, reasonable
pre-terminal exploration, no additional provider requests, metrics, and resume
defaults.

## Interview version

I separated “learned something” from “changed the program.” Reads can be useful
without letting the Agent claim infinite progress. Two proportional soft
checkpoints steer it toward a focused edit; a later typed pause makes analysis
paralysis observable instead of disguising it as a generic step-budget failure.
