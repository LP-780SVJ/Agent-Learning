## Problem

CodeTeam 在 Task 执行中遭遇异构失败时，如何决定下一步动作？

一个 Coding Agent 的每一次运行都会撞上性质完全不同的失败（day3 §一 的 8 种情形）：

1. 模型 API 503 —— 等一会儿重试，大概率自愈
2. API Key 错误 —— 重试永远不会自己变好
3. Patch context mismatch —— 重试同一个 Patch 必然再失败
4. pytest assertion failed —— 重跑测试不能修代码
5. `git reset --hard` 被 Policy DENY —— 重试等于尝试绕过安全策略
6. 用户拒绝 Approval —— 重试等于忽略用户决定
7. Docker Sandbox 不可用 —— 必须 fail closed，绝不能降级裸机
8. 用户 Ctrl+C —— 重试等于无视用户停止请求

如果 Runtime 对以上 8 种情形只有一个回答 `except Exception: retry()`，结果是：该等的没等（8）、不该等的在等（2/3/4）、安全边界被磨损（5/6/7）、用户失去控制权（8）。

W4D3 之前 CodeTeam 的现实正是如此：`orchestrator.py` 的总闸门 `except Exception → _fail()` 将一切失败一视同仁；Week1 的 `codeteam/errors.py` 是 Provider/HTTP 传输层分类（RATE_LIMIT/TIMEOUT/AUTH…），无法表达 `PATCH_CONTEXT_MISMATCH`、`TEST_FAILED`、`POLICY_DENIED` 这些 Agent Runtime 业务语义；`llm/openai_compatible.py` 内还有一套传输层 `RetryConfig`（base_delay=0.5、指数退避）——三处错误处理互不知晓，存在 Retry Storm 风险。

## Context

Day 1 建立了「Natural Language → TaskSpec → Plan → Execution State」，Day 2 建立了「Patch → Verify → Repair → Verify」闭环。前两者回答「做什么」与「做得对不对」；本决策回答「做错以后到底怎么办」（day3 §一百二十二）。

已有资产（实现前核实）：

- `task/state.py`：`TaskState.PAUSED` 已存在；`TASK_TRANSITIONS` 中 READY/IMPLEMENTING → PAUSED（历史存在）
- `planning/models.py`：`replan()` 已存在 → REPLAN 动作直接复用
- `repair/loop.py`：Day 2 RepairLoop 已存在 → REPAIR 动作直接复用
- `verification/models.py`：`VerificationStatus` 六态（PASSED/FAILED/TIMED_OUT/START_FAILED/BLOCKED/INCONCLUSIVE），只有 FAILED 触发 Repair
- `execution/models.py`：`PolicyDecision.DENY`、`ApprovalDecision.DENIED`、`CommandStatus`（含 POLICY_DENIED）——均为结构化返回值，无 raise 路径
- `sandbox/errors.py`：`SandboxError` 异常家族（含 `DockerUnavailableError`、`SandboxMountError`）
- `codeteam/errors.py`：Week1 传输层分类 + `AgentError`，被 `llm/openai_compatible.py` 与 2 个 Week1 测试依赖
- `events.py`：已有 task./verification./repair./approval. 事件族

工业背景（day3 §二）：GitHub Copilot SDK 的 Error Hook 提供 `errorType`/`errorContext`/`recoverable` 让应用决定恢复；OpenAI 明确区分可恢复（429/500/503）与不可恢复（billing/quota/auth）错误并建议 Retry-After 优先、退避次之、避免 SDK/应用层 Retry 叠加；Claude Code Hooks 将 `PostToolUseFailure` 与 `PermissionDenied` 视为不同生命周期事件。共同点是：**错误处理必须知道「在哪一层、哪一阶段失败」，且分类信息由 Runtime 提供、恢复决策由应用层执行**。

## Requirements

1. 同一底层异常在不同阶段必须可映射为不同恢复动作（Timeout 三场景，day3 §三十七）
2. 安全类失败（POLICY_DENIED / APPROVAL_DENIED / SANDBOX_UNAVAILABLE）必须 Fail Closed，且不可随重试次数改变（day3 §四十~四十一）
3. 用户中断（Ctrl+C）必须导向 PAUSED 而非 FAILED（day3 §四十五）
4. 分类必须是 deterministic 的 trusted runtime 行为，不得依赖 LLM 判断（day3 §五十六~五十八）
5. 原始异常信息必须保留（wrap not erase），但用户可见消息必须 sanitize（day3 §十四/十五）
6. 重试必须受次数与总时间双预算约束，且与传输层 Retry 明确分工（day3 §二十六/二十九）
7. 全部行为必须可测试：Policy 不 sleep、测试不真打 API、事件序列可重放

## Alternatives

### Option A: Scattered Exception Handling

各模块自行 try/except + 各自重试（planner.py 一个 Timeout 处理、repair.py 一个、provider.py 一个、session.py 一个 `except Exception`）：

- **优点**: 无新抽象，每个模块按局部理解处理，第一版代码短
- **缺点**: 与 8 种失败情形逐一对照：
  - 同一个 `TimeoutError` 在不同模块语义分裂——Planner 重试、Repair 重试、Provider 重试，形成 day3 §二十八 描述的 3×3×3 Retry Storm
  - 安全失败可能被某个模块的宽 `except` 顺手重试——Policy DENY 从「安全边界」退化为「需要换写法的障碍」（day3 §四十）
  - 恢复语义无统一观测点——「这个 Task 为什么用了 8 分钟」无法从事件流回答
  - 每个模块都要重复实现退避/预算逻辑，且无法统一评测
  - 原始异常在层层 `except` 中丢失（Failure Case 4）

### Option B: Typed Domain Failure（选定）

所有底层失败（Provider exception / Git error / Patch result / Verification result / Security decision）被归一化为共享 `AgentFailure` 域模型，再经 `RecoveryPolicy` 映射为显式 `RecoveryAction`：

- **优点**: 一致的恢复语义；provider 无关（429 与 RateLimitException 同为 MODEL_RATE_LIMIT）；安全规则集中硬编码；可观测（error./recovery./retry. 事件）；可评测（50 Case corpus 数据出口）；支持未来 Session 持久化（AgentFailure 可序列化）
- **缺点**: 更多域类型与映射表需要维护；存在误分类风险（misclassification 是新的失败模式）；映射表与真实 Provider 错误之间需要持续对齐

## Decision

**采用方案 B：Typed Domain Error Recovery。**

```text
Raw Exception / 结构化结果
        │
        ▼
  ErrorClassifier（deterministic，只分类）
        │
        ▼
   AgentFailure（typed domain failure）
        │
        ▼
  RecoveryPolicy（只决策，SECURITY 硬编码 STOP）
        │
        ▼
  SingleAgentOrchestrator（执行：RETRY/REPAIR/REPLAN/REREAD/PAUSE/STOP）
        │
        ▼
  RetryPolicy（只算 delay：backoff + jitter + Retry-After + 双预算）
```

## Why

1. **Consistent recovery semantics** — 同一失败在全系统只有一种语义，`_SIGNALS` 一张表可审计、可测试（50 Case corpus 全绿）
2. **Provider independence** — 429 与 RateLimitException 归一为 MODEL_RATE_LIMIT，AgentLoop 不感知供应商差异（为 Day 5 模型切换铺路）
3. **Safety by construction** — SECURITY 类在三个独立层各自拦截（classifier 表 → RecoveryPolicy 硬编码 → RetryPolicy not_retryable 拒绝），纵深防御不依赖任何单层正确性
4. **Observability** — error.detected → error.classified → recovery.decided → retry.scheduled → retry.started 事件链可重放，回答「Task 为什么用了 8 分钟」
5. **Measurable retry behavior** — Unnecessary/Unsafe Retry Count 可定义、可计数（周度 Benchmark 指标）
6. **Easier fault injection** — 结构化 `FailureCase` dataclass 使 50 案例成为数据驱动测试与周度评测的共同输入
7. **Session persistence ready** — `AgentFailure` 是 BaseModel、`cause` 序列化排除，Day 4 持久化可直接复用

## Trade-offs

- **误分类风险是新的失败模式**：`_STAGE_MESSAGE_MAP` 基于关键词匹配——消息文本变化（Provider 改文案）会导致分类漂移。已接受的缓解：结构化输入（PolicyDecision/VerificationStatus/PatchResult）优先于消息匹配；消息匹配只作兜底；周度 Confusion Matrix 会暴露 TOP 混淆对（day3 §九十二 预期 TOOL vs TEST、MODEL vs CONTEXT）
- **映射表维护成本**：每新增一个 code 需要同步 `_SIGNALS`/`_MESSAGES`/`_STAGE_MESSAGE_MAP` 三处。已接受的缓解：测试断言三表完整（corpus 契约测试）；表是数据不是逻辑，改一行即改行为
- **间接集成证据链**：PolicyDecision/ApprovalDecision/VerificationStatus 是结构化结果（无 raise 路径），不走异常恢复层——它们的 no-retry 保证由 classifier+policy 单测 + Week3 执行层回归 + I3 端到端间接证明（验收报告疑点 B：PARTIALLY_SUPPORTED）。Day 5 接线结果路径后补直接集成测试
- **I4/I5 的集成表达经私有方法**：`TestRecoveryLoopDirect` 直接调用 `_execute_with_recovery`（对应阶段无生产调用方），Day 5 应升级为公共路径测试

### Validation 计划（周度执行规格）

**Benchmark**（day3 §九十一~九十六）：

- 指标：Category Accuracy / Error Code Accuracy / Recovery Action Accuracy / Unnecessary Retry Count / Unsafe Retry Count（+ Confusion Matrix）
- 输入：`tests/failures/fault_cases.py` 的 `FAILURE_CASES`（50 条，可直接 import）；`AgentFailure`/`RetryDecision` 字段已含周度所需信息（category/code/recommended_recovery/retryable/attempt/delay_seconds/should_retry）

**Ablation**（day3 §九十九~一百）：Typed Recovery vs Generic Retry

- Corpus：10 transient / 10 patch / 10 verification / 10 security / 10 permanent
- 指标：Task Success / Total Attempts / Unnecessary Retries / Unsafe Retries / Median Recovery Time / Tool Calls
- 实验假设（待数据验证，非结论）：Generic Retry 对 Rate Limit 有效，但对 Patch mismatch / Test fail / Policy deny / Invalid credentials 不改变导致失败的 State，重试很可能重复同一失败
