# DD-W5-02: Task DAG Instead of Linear Plan for Scheduler Input

## Status

Accepted for Week5 Day2 hardening.

## Evidence Status

IMPLEMENTED_WITH_TESTS. A reproducible DAG micro-benchmark is recorded in
`docs/benchmark/W5_DAG_BENCHMARK.md`. This evidence only covers in-memory DAG
operation cost; it does not prove Multi-Agent speedup.

## Context

Week5 Day1 added Lead/Worker planning contracts. `LeadPlanningResult` contains
an existing `Plan` plus `WorkerAssignment` objects. Day3 will introduce a
Scheduler that needs to know which runtime nodes can be claimed without guessing
from natural language or list order.

## Problem

A linear `Plan.steps` list cannot express fan-out, fan-in, disconnected
subgraphs, or cycles. If the Scheduler consumes only a list, it either serializes
independent work or schedules dependent work too early.

Day2 also exposed two hardening risks:

- `TaskNode` references were mutable outside the graph.
- Omitted dependency information could be misread as "all tasks independent."

Both risks would be amplified by Day3 scheduling.

## Decision

Use an explicit in-memory `TaskDAG` as the Scheduler input boundary.

- DAG edges always reference `TaskNode.node_id`.
- `TaskDAG.from_lead_planning_result()` currently maps
  `TaskNode.node_id = WorkerAssignment.assignment_id`.
- `WorkerAssignment.source_step_id` remains a trace field to the Planner step;
  it is not accepted as a dependency edge ID.
- `dependencies=None` means dependency information was not declared. Multi-node
  plans fail closed with `UndeclaredDependenciesError`.
- `dependencies=()` means the caller explicitly confirmed all nodes are
  independent.
- Non-empty dependency tuples are explicit `(prerequisite_node_id,
  dependent_node_id)` pairs.
- The factory validates before returning, so callers do not receive a cyclic
  DAG from this construction path.

## Adjacency Map vs NetworkX

The implementation uses local adjacency maps:

- `_nodes: dict[str, TaskNode]`
- `_dependencies: dict[str, set[str]]`, where `dependencies[B] = {A}` means
  `A -> B` and B depends on A.

This keeps Day2 small, dependency-free, easy to teach, and easy to audit.
NetworkX would be appropriate later if CodeTeam needs graph algorithms beyond
acyclic dependency management, richer graph metadata, or visualization exports.
It would add a dependency and a larger API surface before Day3 needs it.

## Fail-Open vs Fail-Closed Dependencies

The old default `dependencies=()` was ambiguous because it could mean "not
provided" or "all independent." Day3 would treat both as parallel roots.

The hardened contract is fail-closed:

- `None` plus multiple nodes is an error.
- `()` is an explicit independence declaration.
- A single node with `None` is legal because no inter-node dependency can exist.

This avoids accidental parallel scheduling when the dependency source was simply
omitted.

## Defensive Copies

`TaskDAG` stores a deep copy when adding a node and returns deep-copy snapshots
from `nodes`, `topological_sort()`, and `get_ready_tasks()`. This prevents
external mutation of `node_id` or `status` from corrupting internal indexes.

The tradeoff is copy cost proportional to returned node payload size. For Day2,
nodes are small Pydantic models, and the benchmark measures this cost. If future
nodes carry large artifacts, the runtime can switch to frozen models or thin
read-only projections.

## Topology vs State Ownership

`TaskDAG` owns graph structure and dependency-ready queries. It does not claim
work, run workers, or mark tasks `READY` as a side effect.

Day3 Scheduler owns lifecycle progression:

- deciding when to write `READY`;
- claiming a ready node;
- moving claimed nodes to `RUNNING`;
- recording `COMPLETED`, `FAILED`, or future blocked states.

The only Day2 state write API is `replace_task_status()`, a narrow testable
surface for controlled status replacement. Future concurrent claim should use
atomic compare-and-set semantics, either in the Scheduler state table or a
durable store, so two workers cannot claim the same node.

## Deterministic Order and Complexity

`topological_sort()` uses Kahn's algorithm with a heap of ready node IDs. This
keeps tied nodes deterministic by lexical `node_id`.

The honest complexity is `O((V + E) log V)` in the deterministic heap version,
not strict `O(V + E)`. The extra cost is accepted because deterministic output
makes tests, benchmark evidence, and future Scheduler traces reproducible.

## Current Evidence

- Unit tests cover snapshots, dependency declaration semantics, invalid factory
  edges, cycles, stable topological ordering, and ready queries.
- The benchmark records build, validate, topological sort, and ready resolution
  for 100/500/1000 node graphs across chain, fan-in/out, layered, and
  disconnected shapes.

## Evidence Still Missing

- Day3 Scheduler claim correctness.
- Atomic compare-and-set under concurrent workers.
- End-to-end multi-agent speedup, quality, cost, or latency.
- Real model dependency extraction accuracy.
- Durable DAG persistence and resume behavior.
