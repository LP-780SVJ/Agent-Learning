## Problem

Durable State 决定"存什么"（DD-W4-D4-01）之后，第二个问题：**以什么形态存，才能同时满足快速恢复与完整审计？**

一个 Session 的持久化需求其实是两个不同的问题：

```text
Q1（恢复）：新进程要"接续工作"，需要多快知道"我现在是什么状态"？
Q2（审计/评测/调试）：需要回答"我是怎么走到现在的？"——为什么 Replan？
            失败过几次？什么时候暂停的？每个 Turn 用了什么模型？
```

这两个问题的最优存储形态并不相同。

## Context

工业系统的一致选择（day4 §十七~二十、§三十二）：

- **Snapshot**：某时刻整个 Runtime Domain State 的可直接加载版本（读取代价 O(当前状态大小)，与历史长度无关）
- **Event Log**：按时间追加的 Runtime 事实（回答历史；`session.created / plan.created / patch.applied / verification.failed / checkpoint.created / context.compacted / model.switched / session.paused / session.resumed ...`）
- GitHub Copilot CLI：完整 Session 落文件（Source of Truth）+ SQLite 派生索引（查询用，可从文件重建）——**不为快速查询让索引成为唯一恢复来源**
- Claude Code：持续写本地 transcript（`--resume` 恢复）+ Checkpoint 随 Conversation 保存

已有资产：Week 1 的 `events.py` 已有内存事件（`AgentEvent` + `AgentEventType`）——本决策把它升级为**持久化审计流**；Day 4 的 store.py 已同时实现两条路径（本 DD 是其设计的正式记录）。

## Requirements

1. Resume 快路径：不重放全部历史即可恢复当前状态
2. 审计完整性：状态变化的 from/to/reason 可追溯（何时暂停、为何失败、Replan 几次）
3. 崩溃安全：单条事件写一半不得打不开整个审计史
4. 异常可发现：seq 缺号/重复/乱序可检测（day4 §五十九）
5. Snapshot 与 Event 可对齐：能回答"这条事件发生时快照是什么版本"
6. MVP 不做 Event Sourcing：所有状态重建走 Snapshot，不实现全量 replay

## Alternatives

### Option A: Snapshot only

只存 session.json，每次状态变化整文件重写。

- **优点**: 实现最简单；恢复一次读取即得
- **缺点**: 无法回答 Q2——只知道"现在是 VERIFYING"，不知道"为什么、失败过几次、何时 Replan"；Evaluation（Day 7 的 repair attempts / provider 归因）失去数据源；Debug 靠猜

### Option B: Event Log only（Event Sourcing）

只追加事件，恢复 = 从 event 1 replay 到 N 重建状态。

- **优点**: 完整历史即状态，理论上无信息损失；审计天然完备
- **缺点**: 每次 Resume O(全历史) 重放（5000 事件的 Session 恢复代价高）；replay 逻辑本身是新的正确性风险（事件处理器必须可重放且无副作用）；day4 §十九明确：**第一版不要急着做完整 Event Sourcing**——会突然把项目升级成 Event Sourcing 系统；重放期间与真实世界（worktree）的 Reconciliation 时点也更复杂

### Option C: Snapshot（SoT）+ Append-only Event Log（审计）（选定）

session.json 是 Resume 的唯一权威来源；events.jsonl 只增不删、用于 Audit/Debug/Evaluation。

- **优点**: 恢复 O(当前状态)；审计完备；两文件职责单一；崩溃面隔离（见 Trade-offs）
- **缺点**: 双写（save + append_event）；Snapshot 与 Event 间存在"最后一条事件未落"的窗口；需要 seq/state_version 对齐纪律

## Decision

**采用方案 C：Snapshot = Resume Source of Truth；Event Log = Audit / Evaluation History。不做 Event Sourcing。**

```text
状态变更路径（以 pause 为例）：
  store.save(paused_session)          # ① Snapshot：state_version N→N+1（atomic）
  store.append_event(SESSION_PAUSED,  # ② Event：state_version=N+1 对齐
      state_version=N+1)

崩溃窗口语义：
  ①后②前崩溃 → 磁盘状态正确（PAUSED 已生效），
                审计史少一条 session.paused —— 可接受的最坏损失
  ②写一半崩溃 → partial line，loader 丢弃该行并计数（dropped），
                前序事件完好
```

### 子决策落地表

| # | 子决策点 | 落地 |
|---|---|---|
| 1 | **Source of Truth 单一化** | Resume 只读 session.json（`load()` 不触碰 events）；events 损坏不影响恢复正确性——多文件一致性问题的显式回答（day4 §五十六） |
| 2 | **seq 严格递增 + 抗乱序分配** | `seq` 从 1 起、`Field(ge=1)`；`_last_valid_seq` 用 `max(..., default=0)`（不是 `events[-1]`——中间坏行/乱序时避免撞号）；崩溃重启后 seq 不重复（从文件推导，不依赖内存） |
| 3 | **state_version 对齐** | `SessionEvent.state_version` 记录"事件发生时快照版本"；`SessionManifest.last_event_seq` 内存推进、save 时落盘（内存领先磁盘为既定语义，R7 测试） |
| 4 | **partial line 容忍** | `load_events` 逐行 parse，末尾半行（崩溃残留）丢弃并计数返回 `(events, dropped)`——一条坏行不打不开整个审计史（R8） |
| 5 | **异常可发现** | `find_timeline_anomalies(events)` 纯函数检测 gap/duplicate/out-of-order（如 `"gap: 3→5 (missing 4)"`）；loader 不自动调用（读取零成本），resume 诊断/测试显式使用（R9） |
| 6 | **JSONL 二进制追加** | `open(path, "ab")` + flush + fsync——避免 Windows 文本模式 `\n`→`\r\n` 翻译污染行格式；绝不 `"w"`（截断全部历史） |
| 7 | **context.json 定位为派生状态** | 第三文件是 Derived Context State（坏了可重建，day4 §九十四：version 不匹配 → CONTEXT_STALE → rebuild，不让整个 Session 失败）；Day 5 升级为 model-visible state |
| 8 | **事件命名沿用 dotted 族** | `session.created/paused/resumed/resume_rejected/recovery_required` 与 W4D3 的 `recovery.*`/`task.*` 一致；`retry_scheduled` 旧下划线值不动（O1 命名债务，兼容优先） |
| 9 | **SQLite 后备通道** | `JsonSessionStore` 接口已隔离（create/save/load/append_event/load_events）——未来 `SqliteSessionStore` 换实现，Service/Orchestrator 零改动 |

## Why

1. **Fast recovery** — Snapshot 读取 O(当前状态)；Event 数量增长不影响 resume 主路径（这是周度 Benchmark 的设计验证点：100 vs 1000 events 的 load latency 应基本持平）
2. **完整审计** — from/to/reason 语义保留在事件流（`task.status_changed` 的三字段契约自 W4D1 延续）；Evaluation 的 repair attempts / per-turn provider 归因（Day 5 `turn.*` 事件）直接从 events 统计
3. **崩溃面隔离** — 最坏情况 = 审计史少一条/末尾半行，**状态永不因事件文件损坏而错误**；反过来（event 决定状态）才是危险设计
4. **异常可观测** — timeline anomalies 让"审计史是否完整"可回答，resume 诊断不必盲目信任 events
5. **演进余地** — Event Sourcing / SQLite 两条升级路径都留了接口，而 MVP 复杂度被控制在"两条 append/write 路径"

## Trade-offs

- **双写窗口**：save 成功、event 未写即崩溃 → 审计少一条。已接受：状态正确性优先于审计完备性（SoT 单一化正是为此）；事件丢失可从 snapshot 差分推断
- **seq 分配 O(n) 扫描**：`_last_valid_seq` 每次全文件扫描。已接受：MVP 规模（周度 Benchmark 上限 1000 events）毫秒级；优化路径明确（内存游标 + 崩溃恢复时才全扫，或 SQLite 自增主键）
- **不做 Event Replay 的代价**：无法"回到历史任意时点重建状态"。已接受：当前没有任何用例需要时间旅行；checkpoint 已承担 workspace 层面的回滚，Runtime 状态回滚无需求
- **state_version 对齐纪律**：调用方必须传对齐版本（错传会导致事件史与快照史错位）。已接受：append_event 的 `state_version` 是显式参数而非隐式读全局——错误可见于测试

## Consequences

**落地成果**：

- `store.py`：`save`（atomic + version bump）/ `append_event`（seq 分配 + fsync append）/ `load_events`（容忍 partial + dropped 计数）/ `find_timeline_anomalies`
- `models.py`：`SessionEvent`（event_id/session_id/seq/state_version/type/timestamp/payload）+ `SessionManifest.last_event_seq`
- `events.py`：5 个 `session.*` 枚举（created/paused/resumed/resume_rejected/recovery_required）
- 测试：R6~R9（atomic fault injection / seq 递增对齐 / partial line / anomalies 检测）

**已知限制**：

- `_last_valid_seq` O(n)（周度 Benchmark 后优化）
- `last_event_seq` 内存领先磁盘一个 save 周期
- 事件 payload 无 schema 校验（`dict[str, Any]`）——payload 演进依赖约定

**明确不做清单（本 DD 范围）**：Event Sourcing replay、事件 schema 版本化、后台异步事件 flush（当前同步 fsync）、SQLite 实现。

## When to Revisit

- **周度 Benchmark 后**：load latency 随 events 数量的曲线若明显上升（与设计预期矛盾）→ 检查是否有隐藏的 replay 路径；`_last_valid_seq` 成本量化 → 决定是否优化
- **出现"时间旅行"需求时**（如：回放某个历史时点的 Session 状态做 Failure Analysis）→ 才考虑 Event Sourcing
- **Session 数量/并发增长时**：SQLite（事务跨文件原子性 + 查询索引）；接口已就绪
- **Day 5**：`turn.started/completed` 与 `model.switch_*`、`context.compacted` 事件加入同一 append 流——per-turn provider/usage 归因（Benchmark §四十八）依赖本 DD 的 seq 对齐机制
