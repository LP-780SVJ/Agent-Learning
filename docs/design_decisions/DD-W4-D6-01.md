# DD-W4-D6-01: Thin CLI as Interface Layer

- **日期**: 2026-08-22
- **模块**: `codeteam/cli/app.py`, `codeteam/cli/requests.py`, `codeteam/cli/run_command.py`, `codeteam/cli/render.py`
- **状态**: Accepted（MVP 实现完成）
- **Evidence status**: PROPOSED（CLI E2E 与 Journey Benchmark 周度执行后再升级）

---

## Problem

Week4 Day1-Day5 已经形成 Task、Session、Recovery、Context 和 Model Runtime，但这些能力主要是 Python API。用户需要稳定的终端入口，而不是理解内部类和服务的构造细节。

风险在于：如果直接把 Runtime 组装、Git 操作、Session 对账、模型调用和输出格式都塞进 CLI handler，CLI 会变成 Fat CLI。未来 Web API、IDE 插件、CI 执行器都无法复用同一套 Application Service。

## Context

Day6 引入 `codeteam run/resume/diff/rollback`。这些命令面向人和脚本，是 Coding Agent 的正式 Product Surface。

CLI 的职责是 interface layer：

```text
argv
  -> request DTO
  -> application service / runtime facade
  -> renderer
  -> exit code
```

它不应替代 Agent Runtime、SessionService、GitWorkspace 或 CheckpointManager。

## Requirements

1. CLI handler 只做参数解析和请求对象构造。
2. Runtime 编排放在 `codeteam/cli/run_command.py` 这类 application-facing 模块中，后续可继续抽到真正 service。
3. `diff` 必须是 read-only review surface。
4. `rollback` 必须绑定 Session / Task / Checkpoint ownership。
5. CLI 输出必须能被测试，错误路径不能直接泄露 traceback。
6. 未来 IDE/API/CI 应能复用同一 request DTO 与 service 边界。

## Alternatives

### Option A: Fat CLI

- **优点**: 写起来最快，一个函数能从 argv 一路调到底。
- **缺点**: 业务逻辑散落在 Typer handler 中；Mock 困难；未来 IDE/API/CI 复用困难；容易绕过 Session/Reconciliation/Policy 等已有边界。

### Option B: Script-style `main.py`

- **优点**: 适合一次性 demo。
- **缺点**: 没有稳定 command contract；输出、exit code、错误语义难以长期维护。

### Option C: Strongly Coupled Typer + Runtime

- **优点**: 类型提示和命令定义集中。
- **缺点**: Runtime 被 Typer 绑定；测试需要启动过多真实依赖；迁移到非 CLI surface 成本高。

### Option D: Thin CLI + Request DTO + Renderer（选定）

- **优点**: CLI 可单独测试 argv 映射；Runtime 可被其他 surface 复用；read-only / mutating command 边界清楚。
- **缺点**: 需要多几个小文件和 DTO，初期看起来比直接写 handler 慢。

## Decision

采用 **Thin CLI + Request DTO + Renderer**。

```text
codeteam/cli/app.py
  -> Typer command declarations only

codeteam/cli/requests.py
  -> RunRequest / ResumeRequest / DiffRequest / RollbackRequest

codeteam/cli/run_command.py
  -> CLI-facing application orchestration

codeteam/cli/render.py
  -> stdout / stderr rendering
```

CLI 不自己实现模型调用、Session resume 对账、Git diff 或 checkpoint rollback。它调用已有 service，并把结果渲染成稳定 human/json 输出。

## Why

1. **复用性**：IDE、API、CI 可以复用 request DTO 和 service。
2. **可测试性**：Layer 1 可用 fake service 测 argv -> request；Layer 2 可用 tmp repo 测 integration；Layer 3 可跑 subprocess。
3. **安全边界**：`diff` 不会意外调用 mutation backend；`rollback` 不绕过 CheckpointManager。
4. **可观测**：输出和 exit code 可以成为产品契约，而不是内部异常的副产物。

## Consequences

- `app.py` 中应保持 lazy import，避免 CLI startup 提前加载重 runtime。
- 新命令必须先定义 request DTO，再接 service。
- `diff` 之类 read-only 命令要有测试证明不调用 model/sandbox/mutation backend。
- 当前 `run_command.py` 仍是 CLI-facing orchestration，未来如果继续变大，应抽到 `codeteam/application/` 下的 service。

## When to Revisit

- 如果 CLI command 数量继续增长，拆分 `run_command.py` 为 `run_command.py`、`resume_command.py`、`diff_command.py`、`rollback_command.py`。
- 如果 Web/API surface 开始接入，把 CLI-facing orchestration 下沉为正式 Application Service。
