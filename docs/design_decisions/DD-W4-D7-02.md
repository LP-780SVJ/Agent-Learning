# DD-W4-D7-02: Development and Held-Out Evaluation Split

## Status

Accepted as evaluation policy.

## Context

If every failed task is used to tune prompts, retrieval weights, repair policy, or context compression, that task stops being independent evidence. It becomes a development case.

## Decision

Use a small development/held-out split for the corrected CodeTeam task suite:

```text
Development: 4 tasks
Held-out:     7 tasks
```

Development tasks may be used to debug and tune the harness. Held-out tasks should be run after the harness is frozen.

## Task Mix

The corrected suite removes four CodeTeam-root tasks and keeps 11 tasks against
one `medium_repo` fixture:

| Type | Count |
|---|---:|
| Bug fix | 5 |
| Feature | 3 |
| Refactor | 3 |

It also records difficulty levels from L1 to L4 to avoid measuring only one-line edits.

## Consequences

- README numbers must say which split they come from.
- A task that influenced implementation cannot later be claimed as clean held-out evidence.
- Ablation runs must keep model, provider, budget, repo state, tool set, and hidden oracle fixed while changing only one component.

## Current Evidence

`evals/week4/agent_task_suite_v1.jsonl` records the split and task metadata.
`eval_hidden/week4/` contains the hidden oracle. The corrected null baseline and
non-blind Codex reference outputs live under `evals/week4/agent_runs/`.

## Limitation

The suite is not a general coding benchmark. It is a small engineering
regression and design-evidence suite for CodeTeam's own harness. Real held-out
success rates should not be claimed until the concrete LLM provider endpoint is
approved and the corrected suite is frozen before the run. The Codex reference
run is oracle-informed and therefore cannot be reported as held-out evidence.
