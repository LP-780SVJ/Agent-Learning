# DD-W4-D2-01: Tiered Verification Strategy

- **日期**: 2026-08-18
- **模块**: `codeteam/verification/`、`codeteam/repair/`
- **状态**: Accepted（实现完成）
- **Evidence status**: PROPOSED

---

## Problem

CodeTeam 如何验证每一个候选 Patch？

Repair Loop 每次迭代都会产生一个新 Patch。如果每次 Patch 后都运行完整测试套件：

- 反馈延迟高（假设全量 4 分钟，修 3 次就是 12 分钟纯验证时间）
- 失败证据被稀释（32 个失败里分不清哪个与当前修改相关）
- 迭代成本高（大部分失败的测试与当前 Patch 无关）

如果不做任何验证，则 Task Success 完全依赖模型自我评估——这不是可信 Oracle。

## Context

Day 2 实现验证闭环时，验证范围的选择成为一个核心设计点。已有资产：

- `VerificationService`（语义层验证，走 Week 3 安全链）
- `VerificationKind` 已预留 TARGETED_TEST / RELATED_REGRESSION / FULL_REGRESSION 三级
- `RepairLoop`（max_repair_attempts + S1-S4 停止条件）
- Week 2 的 ImportGraph / SymbolIndex（未来可支持基于 changed-files 的测试选择）

day2.md 二十~二十三节把验证范围建模为"由快到慢的验证漏斗"（Verification Escalation），八十三节正式提出本决策。

## Requirements

1. Repair Loop 的反馈延迟要低（修复质量高度依赖快速获得结果）
2. 失败证据要聚焦（一个明确的 Target Failure 比全量噪声更容易生成 RepairContext）
3. 重复验证成本要低（不是每个 Patch 都值得全量跑）
4. 最终不能失去回归安全（局部正确 ≠ 全局正确）

## Alternatives

### Option A: Full suite after every patch

```text
Patch → 完整测试套件 → Patch → 完整测试套件 → ...
```

- **优点**: 每一步都有最宽验证；不会漏回归
- **缺点**: 慢、贵、反馈噪声多；多数失败与当前 Patch 无关

### Option B: Tiered verification

```text
Patch → Targeted → Related Regression → Full where required
```

- **优点**: 反馈快、聚焦、降低迭代成本；最终仍逐级扩到宽回归
- **缺点**: Target/Related 选择错误时可能漏掉回归；需要测试选择策略

## Decision

**采用方案 B：Tiered Verification（Targeted → Related Regression → Full where required）。**

具体落地：

| 层 | VerificationKind | 触发时机 | Day 2 状态 |
|---|---|---|---|
| Targeted | TARGETED_TEST | 每个候选 Patch 之后 | ✅ 已实现 |
| Related Regression | RELATED_REGRESSION | Target PASS 之后 | ✅ 已实现 |
| Full Regression | FULL_REGRESSION | 预留 | 类型已定义，不执行 |

关键语义：Target PASS + Regression FAILED → 以**回归失败**进入下一轮 Repair（不重修 Target）；Regression 无结论（TIMED_OUT/BLOCKED）→ EXECUTION_ERROR，不默认修代码。

## Why

1. **Feedback Latency** — Repair 的价值高度依赖快速获得结果（day2.md 十八节）
2. **Diagnostic Precision** — 一个明确的 Target Failure 更容易生成 RepairContext（十九节）
3. **Resource Efficiency** — 减少每个 Patch 都全量跑测试的浪费
4. **Regression Safety** — 最终仍逐级扩大验证范围，不是"只跑 Target"（二十节）

## Trade-offs

- **Target Selection 错误是最大风险**：Agent 认为 `test_auth` 足够，但真正受影响的是 `test_sessions`，没被选进 Related——局部回归被漏掉
- **Related 选择策略**尚未实现：Day 2 的 Related Regression 请求由调用方显式传入，未来可基于 changed-files + ImportGraph 自动选择

## Consequences

- `RepairLoop.run` 增加 `related_regression_request` 参数；`_evaluate` 统一处理"target 失败 vs regression 失败"的失败来源
- 周度评测新增指标：Regression Failure Rate After Target Pass（Tiered 策略漏回归的直接度量）
- `VerificationKind.FULL_REGRESSION` 的类型与语义已预留，执行推迟

## When to Revisit

- **周度 Ablation 出结果后**：比较 Tiered 与 Full-suite-per-patch 的 Task Success / 总延迟 / Token 成本，Evidence 升级为 SUPPORTED / PARTIALLY_SUPPORTED / NOT_SUPPORTED
- **实现 changed-files + ImportGraph 测试选择后**：Related Regression 的自动选择需要独立评测
- **Target 选择错误率可量化后**：若漏回归率过高，考虑在 SUCCESS 前强制 FULL_REGRESSION

## Evidence

- **状态**: PROPOSED — 实现已完成、66 个单元/集成测试覆盖级联语义，但**未执行**：
  - Benchmark（验证延迟/成本）—— 周度集中评测
  - Ablation（Tiered vs Full-per-patch 的 Task Success）—— 周度集中评测
- 不声称 Tiered 策略有可量化的优势；"分层验证更快且不漏回归"目前是工程假设，不是数据结论。
