## Context

Day3 WorkerRegistry stored identity and Worker objects; TaskScheduler owned
availability and task ownership. That separation was intentional, not two
competing dynamic-state authorities. Heartbeats, loss detection and restart now
require dynamic Worker state independent of task claim operations.

The previous `start/complete/fail(node_id, worker_id)` interface could not
distinguish two attempts owned by the same Worker. Restart also creates stale
Worker callbacks that cannot be identified by worker_id alone.

## Requirements

- Mandatory task-attempt fencing before enabling timeout/retry.
- Worker generation fencing plus revision/reservation revalidation.
- One Worker dynamic-state authority and one Task/ownership authority.
- Atomic Task, Worker, queue, ownership and audit updates.
- CLAIMED and RUNNING recovery, bounded retry and bounded logical restart.
- STOPPED never auto-reactivates; terminal Tasks never resurrect.
- Clock injection, explicit deadline boundary, no callbacks under core lock.
- Mailbox messages and heartbeats do not directly complete Tasks.

## Decision

`AgentRegistry` owns Worker status/generation/revision/heartbeat/restart state.
`TaskScheduler` owns task status/attempt/ownership and its derived occupancy index.
`AgentInfo.status` remains a bootstrap input, not a live projection. Read current
availability through `registry.runtime(worker_id)`. `compatible(role)` answers
role compatibility only. Bootstrap BUSY means unavailable, not an invented owner.

`TeamStateCoordinator` owns one RLock, runtime_id and audit transaction sequence.
A coordinator binds one Registry and one Scheduler. Lifecycle delegates to those
objects; it has no separate Agent state table and never selects a successor.

All mutation APIs use rollback-backed copy-on-write drafts under the shared lock.
Registry and Scheduler keep old reference sets; their new dict/deque/set/history
references are private to the lock holder while validation/events/results are
prepared. Any preparation exception restores both sets before unlock. Successful
transaction exit publishes the complete draft; no external callback executes in
that block. Ordinary read methods and combined `scheduler.snapshot()` acquire the
same lock. This is not a database transaction or crash-durable commit.

Core lock ordering: shared coordinator lock, then package-internal helpers; release
it before event sinks/factory. Do not acquire Session/Mailbox/Git/Docker locks or
run tools inside the core transaction. Registry's injected Clock must be short,
non-reentrant and free of I/O.

Task APIs now require returned `TaskClaim`; `claim` requires `WorkerLease`.
No bare-worker overload infers a current attempt. Claim checks runtime, worker,
attempt and worker_generation; Worker operations check the lease epoch/generation.
Registry `lease(worker_id)` is trusted discovery for a new operation, never a
mechanism to refresh a delayed completion/heartbeat into a new authorization.
WorkerRegistry and its exceptions retain public import identity as aliases, not
a parallel implementation.

Timeout uses injected monotonic time; exact `elapsed >= timeout` expires. A
READY/BUSY registration, activation or restart publication receives initial grace
at its local receipt time. Heartbeats only update READY/BUSY and increment revision
even at an identical clock reading. Nonfinite, negative or backward clock readings
fail explicitly. The last accepted clock reading is observational state, not a
heartbeat: even an aborted business transaction cannot make accepted time rewind.
Audit timestamps remain wall clock.

Scan returns an immutable candidate including generation, revision, last heartbeat
and owned task attempt. Recovery rechecks it under the shared lock with fresh
time. Stale candidates do not revoke ownership or consume retry/restart budget.
Valid loss makes Worker FAILED and clears CLAIMED/RUNNING ownership together;
attempt remains unchanged. Only the next successful claim increments attempt.
Tasks requeue once only when `attempt < max_attempts`; otherwise they remain FAILED
and dependents become BLOCKED. Stop uses the same bounded task revocation policy
but publishes STOPPED, not FAILED.

Restart is reserve/build/publish. Reserve consumes one lifetime attempt and sets
cooldown, then the synchronous factory runs outside the lock. It must construct
a new Worker facade preserving id/display_name/role/capabilities. A matching
reservation publishes READY and generation+1 with fresh grace. Failure consumes
budget but does not change generation; late success/failure is rejected. A stopped
or newer Worker cannot be overwritten. KeyboardInterrupt/SystemExit clean a
matching reservation before propagation. Factory failure does not undo task
requeue. Sweep considers prior FAILED Workers again but never retries unboundedly.

Defaults are teaching configuration: timeout 15s, restart cooldown 2s,
max_restarts 2; max_restarts=0 disables factory attempts. Cooldown begins at reserve,
budget counts factory reservations over this runtime lifetime and is not reset by
success. No heartbeat driver is introduced.

## Alternatives

| Option | Benefit | Why not selected |
| --- | --- | --- |
| alive bool + owner_id | Small model | Cannot reject same-owner late attempts or distinguish stop/restart |
| Independent Registry/Scheduler locks | Local isolation | Does not supply a cross-object transaction; lock order and rollback still needed |
| Shared coordinator and drafts | Inspectable linearization point | Copying and lock contention must be measured; no throughput claim |
| New worker_id on every restart | Avoids some identity reuse | Does not solve same-generation task retry fencing |
| One giant Lifecycle scheduler | Single object | Blurs task scheduling and liveness responsibility |
| SQLite / workflow / actor runtime | Durable/distributed options | New protocols, not necessary for this in-process foundation |

## Consequences

The same Worker can retry safely at the control-plane submission boundary. A
timeout means loss of trusted execution eligibility, not proof of process death.
Fencing does not terminate an old process or make external effects exactly-once.
Raw control-plane objects are trusted capabilities, not exposed to the LLM.

Factory is synchronous, short and no-I/O by contract. A stuck factory can block its
caller indefinitely, although it does not hold the core lock; another thread may
stop it logically, invalidating its eventual callback. Count-bounded is not
time-bounded. WorkerExecutor, real process cancellation, SQLite, cross-process
lease reconciliation and Team Session resume remain out of scope.

Current Runtime and SafeExecution do not understand Team tokens. A future adapter
must bind task/worktree authority and fence result submission; it must not hold
the shared lock across model/tool execution. Session persistence must serialize
durable facts, not Worker objects, locks or cross-process monotonic timestamps.

Audit has scalar metadata, transaction_id/event_index, generation/attempt and
safe reason codes. Observer delivery is best-effort outside the lock; failed
delivery does not undo a successful mutation. Audit order is transaction order,
not callback-arrival or wall-clock order. Histories grow for the runtime lifetime;
neither retention nor copy cost is globally bounded.

## 2026-09-01 Acceptance Corrections

### P1: Committed Reservation Interrupt Ownership

The original interrupt claim above was incomplete: factory interruption was
covered, but `reserve_restart()` delivered WORKER_RESTARTING after commit and
before returning its ticket. A KeyboardInterrupt/SystemExit in that observer left
RESTARTING behind because Lifecycle never received the reservation to clean.
Both original tester instances were reproduced unchanged before editing.

Decision: handle that interrupt in Registry while the actual local RestartTicket
is available. Factory interruption and reservation-observer interruption share
the package-internal `_interrupt_restart()` path. It uses the existing transactional
ticket check (runtime_id, generation, restart_id, expected revision and RESTARTING),
not a newly fetched lease. Matching state changes to FAILED and clears restart_id;
the original Worker, generation, consumed budget, cooldown and earlier task
recovery remain unchanged. A stale ticket adds rejection evidence only.

Reservation and cleanup are separate committed facts and retain separate audit
transaction IDs linked by restart_id. Cleanup reason is `restart_interrupted`,
not an assertion that the uncalled factory failed. The existing outcome enum is
retained internally; interruption never returns a successful restart outcome.

Cleanup event delivery occurs after commit and outside the core lock. Its narrow
interruption-delivery helper records a secondary observer failure and attaches a
safe type-only note to the original interrupt, then the caller re-raises the
original exception object. Delivery-error audit failure also adds a note instead
of replacing the original interrupt. Normal event delivery still propagates
KeyboardInterrupt/SystemExit; this is not a global BaseException suppression rule.

Alternatives considered:
- Widen only Lifecycle's try: insufficient because no actual ticket was returned.
- Fetch the latest lease and reset: can erase STOPPED or a newer reservation.
- Roll back reservation after observer failure: falsifies a commit observers may
  already have seen and incorrectly refunds its budget.
- Suppress all process-control exceptions globally: violates interruption semantics.
- Drop cleanup notifications entirely: avoids recursion but loses best-effort
  observer delivery; selected explicit secondary-failure handling instead.

Limits: these are synchronous injected callback interrupts, not proof against
SIGKILL, OOM or arbitrary repeated OS signals during internal preparation. A
factory that never returns is still not preempted. If delivery-error recording
itself fails, the original exception note is the remaining diagnostic; no durable
audit guarantee is claimed.

### P2: Terminal Dependency Closure in One Transaction

The original sorted-ID single pass could examine A before M in Z -> M -> A, then
block only M. Four unchanged tester instances reproduced this for timeout/stop
and CLAIMED/RUNNING. The same helper also affected terminal normal fail.

Decision: cache node IDs from the existing `TaskDAG.topological_sort()` at Scheduler
initialization, alongside the topology/dependency snapshot. In `_schedule_locked`,
first compute the terminal-blocked closure using that order. Each prerequisite
is resolved before its descendants. Then apply actual PENDING -> BLOCKED changes
in the existing sorted-ID pass; queue order and unrelated scheduling stay stable.
No call to the subsequently mutable original DAG is needed.

The closure visits each node once and at most each dependency once: O(V + E),
with O(V) set storage. The finite cached order guarantees termination; no retry
scan or caller-triggered extra schedule is needed. Building that order uses the
existing heap-based DAG method (O(V + E + V log V), excluding snapshot copy costs).
Overall Scheduler work still includes its prior ID sorting, role lookup and draft
copy costs; this is not a new linear-time claim for the entire scheduling method.

Transient retryable failures are READY before later scheduling, so they do not
seed the terminal closure. Timeout, stop, exhausted normal fail and non-retryable
normal fail use the same closure. Blocked descendants remain ownerless and outside
the READY queue. Each real transition emits once in the terminal transaction.
The existing shared draft rollback restores Worker, Task, membership, queue,
events and audit counters if a descendant event preparation fails midway.

Alternatives considered:
- Repeat schedule until stable: leaks incomplete state or adds unbounded calling
  conventions; repeated full scans can reach O(V * (V + E)).
- Traverse all scheduling in topological order: changes existing lexicographic
  ordering of ready work and event output; closure-first preserves that convention.
- Maintain a new reverse-edge worklist implementation: viable, but duplicates
  existing DAG capability for this scoped correction.
