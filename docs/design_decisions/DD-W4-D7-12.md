# DD-W4-D7-12: Narrow Verification-sandbox Environment Introspection

## Status

Accepted and implemented offline on `week4`; real-provider validation is pending.

## Problem

F03 repeatedly asked whether PyYAML was installed. Project declaration evidence
and runtime availability are different facts, and host availability says
nothing about the actual verification Docker image. Existing safe execution
correctly denies model-authored `python -c`, and the Runtime must not relax that
boundary just to answer a dependency question.

## Alternatives considered

1. Let the model run `python -c`: rejected; arbitrary interpreter code bypasses policy intent.
2. Add generic `run_command`: rejected; expands the production capability surface.
3. Hardcode PyYAML: rejected; fixture-specific and not provider neutral.
4. Infer only from `pyproject.toml`: insufficient; declared packages may be absent and image packages may be undeclared.
5. Fixed Runtime-owned Docker probe with a narrow schema: selected.

## Decision

`inspect_environment` accepts exactly one validated `python_module` or bare
`executable`. Module names match `[A-Za-z_][A-Za-z0-9_.]*`; executable names are
bare tokens. Runtime supplies a fixed Python probe to the same read-only Docker
boundary used by verification. The model supplies no code, flags, shell text,
cwd, image, or environment. Module discovery uses `PathFinder` without importing
the target; executable discovery uses `shutil.which` without execution.

The result reports `runtime_available`, `declared_by_project` as
true/false/unknown, `environment=verification_sandbox`, and an explicit
non-portability warning when the image happens to provide an undeclared module.

## Invariants

- Host Python is never treated as verification evidence.
- Runtime availability is never conflated with project declaration.
- Inspection does not alter workspace version, verification evidence, or completion readiness.
- Agent-authored `python -c`, shell strings, pipes, and generic commands remain denied.
- Probe execution is read-only, no-network, and model argument validation is fail closed.

## Trade-offs and limitations

Python import-package names do not always equal distribution names, so declaration
comparison is intentionally conservative. This is a diagnostic affordance, not
a dependency resolver, package installer, or generalized shell. Other languages
need explicit future adapters.

## Verification

Tests cover sandbox true/false independent of host state, declared/undeclared,
declared-but-missing, executable probes, invalid names, ambiguous requests,
fixed argv ownership, read-only profile, and the unchanged CommandPolicy denial
of `python -c`.

## Interview version

I did not weaken command policy to answer “is this dependency present?” I added
a capability-specific observation: the model asks a typed question, Runtime
builds a fixed non-importing probe, Docker answers for the real verification
environment, and the result separately states whether the project declared it.
