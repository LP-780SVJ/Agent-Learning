# DD-W4-D7-14: Finalization-aware Step Budget

## Status

Accepted and implemented offline on `week4`. Real-provider stability validation
is pending user execution.

## Problem

A flat model-step budget allowed complex tasks to consume all turns before
deterministic completion requirements could be finalized, causing correct work
to be reported as `MAX_STEPS`. In the 2026-08-30 campaign, all 40 external
grader results were correct while Actor success was 38/40. F03 became READY on
turn 20 after `git_diff`, but had no turn 21 for `submit_result`. F04 made a late
valid workspace mutation, correctly staled prior verification, and exhausted a
run-level cap of 20 despite declaring 30 task steps.

## Alternatives

1. Increase `max_steps`: rejected because it shifts the boundary, changes the
   experiment, and does not solve finalization starvation.
2. Grant free LLM finalization turns: rejected because it hides Provider work
   outside the declared budget.
3. Relax current-version completion evidence: rejected because stale tests or
   stale diff review would become completion authority.
4. Runtime terminal settlement only: necessary for READY-at-boundary, but does
   not help a late patch reserve time for re-verification.
5. Finalization reserve only: improves orchestration, but the last legal action
   may still be the action that makes the gate READY.

## Decision

Use both mechanisms inside the existing effective budget:

- `FinalizationBudgetPolicy` deterministically reserves
  `max(3, ceil(effective_max_steps * 0.20))` turns unless explicitly overridden.
  For this campaign, effective 20 means reserve 4.
- A real diff plus remaining turns at or below the reserve enters finalization
  advisory mode. The advisory carries remaining turns, the CompletionGate's
  missing requirements, exact task/regression commands, current diff-review
  state, and a warning to avoid optional diagnostics. It remains legal to patch.
- At the model-step boundary, Runtime first honors any safety halt. If the
  current CompletionGate is READY, it recomputes a fresh workspace content
  fingerprint and settles without another Provider call only when it matches
  the fingerprint attached to Runtime evidence.
- Completion provenance is explicit:
  `model_submitted` or `runtime_budget_boundary_settlement`.
- When READY, `submit_result` is accepted, a real `apply_patch` reopens the
  task, and the first targeted read/search remains legal. Redundant test,
  environment, list, status, and diff calls are skipped with an advisory.
  Multi-call batches recompute the gate before every call.

## Invariants

- Step budget limits further model work; CompletionGate decides whether the
  existing work is complete.
- Terminal settlement never calls the Provider and never uses the hidden
  grader.
- NOT READY remains `MAX_STEPS` at the boundary.
- Current-version verification, diff review, safe real diff, workspace hygiene,
  and no pause remain mandatory.
- Fresh fingerprint mismatch refuses settlement and pauses as workspace drift.
- Finalization reserve is part of, not in addition to, `max_steps`.
- Safety halt has priority over READY, READY over finalization advisory, and
  finalization advisory over ordinary progress guidance.
- No submit-time automatic verification is introduced.

## Budget provenance

Evaluation records task-declared steps, run-level cap, effective steps, and the
source of the effective value. The user-run stability script explicitly passes
`--max-steps 20`; thus B02/B05 (25) and F04/R02/R03 (30) remain effective 20 for
causal comparison rather than silently depending on a default.

## Trade-offs

The reserve is deterministic and observable but is not a semantic phase
planner. READY tool convergence can save expensive calls, but a targeted read
still consumes a turn. Runtime fallback summaries are deliberately bounded and
factual, so they are less expressive than a model-written summary.

## Verification

Deterministic tests cover default/override reserve boundaries, F03
READY-on-last-turn settlement, NOT READY and stale-evidence failures, fresh
fingerprint mismatch, late-patch F04 advisory, READY reopen/skip/read behavior,
per-call batch recomputation, Session/event/eval provenance, declared/capped
budgets, and stability aggregation false negatives. The coder runs only script
syntax and dry-run checks; the real F03 x5, B01 x2, 11-task x3 campaign remains
pending user execution.

## Limitations

- Finalization reserve is budget-aware, not a full semantic phase planner.
- Terminal settlement only applies when current Runtime evidence is already READY.
- Environment introspection portability classification may still be coarse.
- Task-declared and run-level budget policy remains a separate product decision.
