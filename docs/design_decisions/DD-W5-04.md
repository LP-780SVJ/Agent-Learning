# DD-W5-04: In-Process Mailbox Instead of Direct Agent Calls

## Status

Accepted for Week5 Day4 foundation.

## Evidence Status

IMPLEMENTED_WITH_TESTS_AND_SAFETY_ABLATION. A reproducible in-process Mailbox
benchmark is recorded in `docs/benchmark/W5_MAILBOX.md`, but that benchmark is
now `STALE_AFTER_HARDENING / RERUN_DEFERRED_UNTIL_WEEK5_COMPLETION` because
`mailbox.py` changed after the measurement. The safety ablation in
`docs/benchmark/W5_MAILBOX_ABLATION.md` compares atomic broadcast with a looped
`send()` implementation. This evidence covers local mailbox correctness and
safety tradeoffs; it does not prove Multi-Agent speedup, crash recovery,
durable replay, or exactly-once delivery. Final supported status remains for
tester acceptance.

## Context

Week5 Day1 introduced Lead/Worker identities and assignments. Day2 introduced
TaskDAG topology. Day3 introduced an in-process Scheduler with atomic task claim
and runtime ownership. Day4 needs a communication layer for Lead and Worker
agents to exchange structured messages without directly calling each other.

## Problem

Direct function calls couple Agent lifecycles and make it hard to express:

- a receiver that is idle, busy, or not polling yet;
- queued progress or review findings;
- per-recipient FIFO delivery;
- bounded inbox capacity and backpressure;
- audit events for communication without logging full payloads;
- broadcast without partial delivery.

Agent communication must also avoid bypassing the Day3 Scheduler. A
`TASK_COMPLETED` message is communication, not permission to mutate task state.
Actual state transitions remain owned by `TaskScheduler.complete()` and
`TaskScheduler.fail()`.

## Requirements

- Keep the first Mailbox in-process and non-durable.
- Use synchronous APIs to match the Day3 Scheduler core.
- Use `AgentIdentity.agent_id` as the Mailbox address.
- Do not reuse `WorkerRegistry` as a Mailbox address book because Lead agents
  also need inboxes and worker availability is not message reachability.
- Keep `AgentMessage` separate from LLM `Message` and audit `AgentEvent`.
- Provide per-inbox FIFO by successful enqueue linearization order.
- Use bounded capacity and fail closed with `MailboxFullError`.
- Reject unknown senders/recipients and duplicate message IDs.
- Reject broadcast batches that generate duplicate message IDs before any
  inbox, seen-ID, or event mutation.
- Validate `AgentMessage.payload` as a JSON-compatible object at construction
  time and require `created_at` to be finite and non-negative.
- Make broadcast all-or-nothing.
- Emit safe audit metadata without logging full payloads.
- Deliver external event sinks outside the Mailbox lock.

## Decision

Implement `AgentMailbox` with:

- `threading.Lock` around address book, inboxes, seen message IDs, and internal
  event history;
- `collections.deque` per registered agent inbox;
- `AgentMessageType` and `AgentMessage` Pydantic models;
- independent Mailbox address registration for Lead and Worker identities;
- destructive non-blocking `receive()`;
- global accepted-message ID dedupe;
- all-or-nothing `broadcast()` over explicit recipient IDs;
- batch-level broadcast message-id uniqueness checks;
- JSON-compatible payload validation and finite non-negative timestamps;
- Day3-style best-effort event sink delivery outside the state lock.

The delivery guarantee is intentionally modest:

```text
in-process
non-durable
per-recipient FIFO
destructive receive
at-most-once dequeue
bounded capacity
no silent drop
```

## Alternatives

### A. Direct Agent Calls

Simple and fast for demos. It does not provide queued communication, receiver
decoupling, message audit, backpressure, or broadcast atomicity.

### B. In-Memory deque + Lock Mailbox

Matches the current synchronous Scheduler, has no new dependency, and makes
linearization points easy to test. It loses messages on process crash and does
not support cross-process agents.

### C. asyncio.Queue

Useful for an async Worker loop, but it would introduce event loop ownership
before the current runtime needs it. It also would not solve address
registration, duplicate message IDs, safe events, or atomic broadcast by itself.

### D. SQLite or Durable Queue

Required for crash recovery and replay. Deferred because Day4 is the
communication foundation; durable Team Task Store belongs to Day6.

### E. External Broker

Systems such as Redis, NATS, or Kafka can provide stronger deployment and
scaling properties. They add infrastructure and failure modes that would hide
the local Agent Runtime invariants this project is currently learning.

## Consequences

- Lead and Worker agents can exchange structured messages without direct calls.
- Busy Workers can still receive messages; availability is a Scheduler concern,
  not a Mailbox registration concern.
- Message payloads stay out of audit events.
- Broadcast has one clear transaction boundary.
- The Mailbox is easy to benchmark and test under threads.

The cost is that Day4 does not survive process crash and cannot claim
exactly-once semantics.

## Memory Retention Tradeoff

`capacity_per_inbox` only bounds the number of currently queued messages in a
single inbox. It does not make total `AgentMailbox` memory bounded:

- `_seen_message_ids` grows with every successfully accepted message so global
  lifetime dedupe can reject replayed IDs even after destructive receive.
- `_events` grows with registration, send, receive, broadcast, and delivery
  failure audit facts.
- queued payload memory is bounded per inbox, but cumulative dedupe and audit
  metadata are intentionally retained for Day4 correctness and observability.

The first implementation should therefore be scoped to a team, task, or session
lifecycle and released when that lifecycle ends. Dedupe windows, event archival,
durable replay, persisted dedupe, and recovery policies are deferred to Day6.
This is a correctness-versus-memory choice, not a claim that the in-memory
Mailbox is globally bounded.

## Current Evidence

- Unit tests cover model validation, independent Lead/Worker address
  registration, unknown agents, duplicate agents, point-to-point send/receive,
  empty inboxes, FIFO, duplicate message IDs, broadcast batch duplicate
  generated IDs, JSON payload validation, finite timestamp validation,
  defensive payload copies, capacity limits, all-or-nothing broadcast, Mailbox
  not mutating Scheduler state, concurrent producers, safe audit metadata,
  event sink reentry, sink exception isolation, and public API exports.
- `evals/week5/benchmark_mailbox.py` measures setup, send, receive, concurrent
  producer send, broadcast fan-out, and approximate backlog size. Its current
  report is stale after hardening and will be rerun after Week5 completion.
- `evals/week5/ablation_mailbox.py` runs a deterministic safety ablation. In
  four failure workloads, full atomic broadcast produced zero partial
  deliveries while the looped-send ablation produced partial delivery in every
  workload.

## Evidence Still Missing

- Worker crash recovery after destructive receive.
- Ack/nack and message retry.
- Durable replay and resume.
- Cross-process ordering and distributed backpressure.
- End-to-end Multi-Agent success, cost, or latency improvement.
- Global memory bounding for lifetime message-ID dedupe and event history.

## When to Revisit

Revisit this decision when Day5 heartbeat/crash detection and Day6 durable Team
Task Store exist. At that point, compare this in-memory mailbox with a durable
queue that can restore unprocessed messages and reconcile in-flight receives.
