# DD-W5-03: State Machine Scheduler Instead of Direct Async Fan-Out

## Status

Accepted for Week5 Day3 foundation.

## Evidence Status

IMPLEMENTED_WITH_TESTS. A reproducible in-process Scheduler benchmark is
recorded in `docs/benchmark/W5_SCHEDULER.md`.

## Context

Week5 Day1 introduced Lead/Worker assignment contracts. Week5 Day2 introduced
`TaskDAG` as the dependency graph between runtime task nodes. Day3 needs a
component that decides which dependency-ready node is queued, claimed, started,
completed, failed, or retried.

## Problem

Directly running several workers with `asyncio.gather()` does not answer core
runtime questions:

- Has this task already been queued?
- Which worker owns it?
- Can a busy worker claim another task?
- Can a non-owner complete or fail a task?
- What happens when two workers race for the same ready task?
- How are retries bounded?

These are Scheduler state-machine concerns, not LLM reasoning concerns.

## Decision

Implement an in-process synchronous `TaskScheduler` core using:

- `threading.Lock` for one critical section around queue, status, ownership,
  attempt, and worker availability updates.
- `collections.deque` for the ready queue.
- `TaskRuntimeRecord` as the Scheduler runtime state source of truth.
- `TaskClaim` as a structured claim result.
- Explicit transition table over the existing Week5 `TaskStatus` enum.

`TaskStatus.CLAIMED` is added to the existing Day2 enum. The project does not
create a second task state vocabulary.

## State Vocabulary

The Scheduler uses:

```text
PENDING -> READY -> CLAIMED -> RUNNING -> COMPLETED
                                  |
                                  v
                                FAILED -> READY  # bounded retry
PENDING/READY -> BLOCKED
```

`CREATED` from the initial Day3 prose maps to `PENDING`. `SUCCESS` maps to
`COMPLETED`. `RETRYING` is not a first-version state; retry is represented as
`FAILED + attempt + retry decision`, then a bounded transition back to `READY`.

## Source of Truth

`TaskRuntimeRecord.status` is the Day3 runtime state source of truth.
`TaskDAG` remains the topology source of truth through its node IDs and
dependency map. `WorkerAssignment` remains a Lead planning contract and does not
store owner, attempt, claim time, or failure reason.

IDs are deliberately separate:

- `node_id`: Scheduler and DAG runtime key.
- `assignment_id`: assignment identity; currently used as factory node ID.
- `source_step_id`: Planner trace field.
- `owner_id`: Worker identity.

## Synchronous Core vs Async Core

The synchronous core keeps state correctness independent from an event loop.
This fits the current repository, where tests and most runtime services are
synchronous. An async worker runner can wrap the Scheduler later, but the claim
linearization point stays inside the synchronous lock.

An async-first core would be useful when worker execution is fully async, but it
would mix event-loop ownership with the Scheduler's core invariant before the
project needs it.

## Alternatives

### Direct `asyncio.gather`

Simple for demos, but it has no persistent task status, no ownership, no retry
budget, and no reliable way to reject duplicate claim.

### `asyncio.Queue`

Works well with async APIs, but the Day3 API is synchronous and the state
correctness does not require an event loop.

### `queue.Queue`

Provides a thread-safe queue, but queue locking is separate from ownership and
worker availability. The Scheduler still needs its own lock, so using `deque`
keeps the invariant easier to audit.

### Durable Scheduler Store

Needed for Day6 resume and cross-process safety. It is intentionally deferred
because Day3 only proves single-process thread-level correctness.

## Current Evidence

- Unit tests cover idempotent schedule, worker role and availability gates,
  duplicate claim contention, multi-worker claim uniqueness, owner-only
  complete/fail, invalid state progression, bounded retry, and scheduler events.
- `WorkerAgent.info` now returns defensive snapshots, so Registry identity keys
  are not corrupted by public `AgentInfo` mutation.
- Scheduler events are emitted through `codeteam.events`, not a new logging
  system.
- `evals/week5/benchmark_scheduler.py` measures schedule latency, claim
  throughput, and contention failure rate.

## Evidence Still Missing

- Cross-process or distributed claim.
- Worker crash detection and heartbeat.
- Durable queue recovery and Session resume.
- Mailbox coordination.
- Worktree/file ownership integration.
- End-to-end Multi-Agent success, cost, or latency improvement.
