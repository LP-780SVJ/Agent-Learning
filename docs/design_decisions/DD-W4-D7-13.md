# DD-W4-D7-13: Explicit Initial Context Snapshot Reuse

## Status

Accepted and implemented offline on `week4`.

## Problem

Initial retrieval can already contain a complete current file, but a later
`read_file` repeats the full content. Prompt advice alone cannot safely suppress
the call because compressed, partial, stale, or compacted-away content must not
be mistaken for a complete visible copy.

## Decision

Runtime constructs an `InitialContextSnapshot` directly from
`ContextBuildReport` before message serialization. Each entry records path,
content, SHA-256, compression level, workspace version, and completeness. Only
`FULL_FILE` at the current version can satisfy a full read.

If that exact file is still present in the current `ModelRequest`, `read_file`
returns a compact structured reference to the request copy. If compaction has
removed file content, it returns the cached complete content. Ranged reads and
compressed entries use the real file tool. Any workspace-version change or
resume without a fresh explicit snapshot invalidates reuse.

Initial-context hits have separate counters and do not advance the legacy
cached-no-progress counter. The behavior never fabricates list/search results.

## Invariants and limitations

- Runtime does not parse the serialized user message to reconstruct snapshot facts.
- Hash equality is evidence identity, not semantic equivalence.
- A reference saves repeated output tokens but the original request content still consumes input budget.
- Resume deliberately drops ephemeral snapshot reuse unless a new snapshot is built.

## Verification

Tests cover visible reference, compacted full fallback, compressed/partial
rejection, version invalidation, same-turn multi-read pairing without
`NO_PROGRESS`, and a deterministic token-estimate reduction.
