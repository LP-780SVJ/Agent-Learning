# DD-W4-D7-15: Batch-aware Stall Detection

## Status

Accepted and implemented offline on `week4`. Real-provider stability validation
is pending user execution.

## Problem

Native providers can emit multiple tool calls in one assistant turn. The legacy
cached/repeated-action guard evaluated progress after each individual call and
could terminate the entire Agent before later fresh calls in the same batch
were executed. In the user-run campaign
`evals/week4/agent_runs/stability_20260830_102307`, Actor success was 39/40 and
security was 40/40. The only failure was F03: turn 11 declared a cached
`read_file("AGENTS.md")` followed by two fresh reads. The first cache hit raised
the per-call counter to two and returned `NO_PROGRESS`; the fresh reads received
no ToolResult and the run ended with 0 patch attempts.

The trace proves a lost Runtime execution opportunity. Because the dropped
calls were reads rather than a patch, it does not prove the model would
certainly have completed the task.

## Alternatives

1. Raise the cached/repeated threshold: rejected because it only lowers the
   reproduction probability while retaining the wrong decision granularity.
2. Remove the guards: rejected because pathological mechanical loops would no
   longer stop promptly.
3. Rely only on `ProgressPolicy`: rejected because that policy owns long-lived
   source-state progress, while a short exact duplicate loop remains a useful
   independent control.
4. Aggregate the safe batch and decide once per model turn: selected because it
   preserves loop protection without discarding later fresh work.

## Decision

- Cache and repeated-action detection remains per call, but mechanical stall
  classification happens only after all safe executable calls in the turn have
  been considered.
- Multiple cached/repeated calls in one assistant turn add at most one to the
  mechanical stall streak. Two wholly stalled turns retain the existing bound.
- Any uncached observation, including a failed but newly executed diagnostic,
  prevents that turn from being classified as wholly stalled. A successful
  `apply_patch` additionally advances workspace/source progress through the
  existing Runtime observer.
- Repeated non-destructive exploration (`list_files`, `read_file`,
  `search_code`, `inspect_environment`, status/diff cache reads, and
  semantically equivalent `run_tests`) is skipped with a correlated cached or
  structured duplicate ToolResult; later safe calls continue.
- Repeated `apply_patch`/`submit_result` retains destructive/control fail-fast
  behavior. Mixed `submit_result` batches remain rejected without execution.
- Tool budget exhaustion and an active Runtime/sandbox halt may stop in the
  middle of a batch. Remaining calls receive correlated rejection results and
  are accounted as safety/budget rejection, not progress-guard loss.

## Invariants

> A model turn must not be classified as stalled until all safe executable tool
> calls in that turn have been considered.

> Multiple cached tool calls inside one turn count as at most one stalled turn.

> Any fresh observation or source progress in the same batch prevents that turn
> from being classified as fully stalled.

Fresh observation means an observation not returned from the action cache; it
does not mean source progress. `ProgressTracker` diagnostic observations still
do not reset its source clock. Safety, tool-call budget, native call correlation,
SafeExecution, CompletionGate, finalization reserve, and terminal settlement
remain unchanged.

## Repeated action semantics

| Batch action | Decision |
|---|---|
| repeated exploration only | skip, emit ToolResult, count at most one stalled turn |
| repeated exploration + fresh read/search | skip duplicate, execute fresh call, turn is not stalled |
| repeated exploration + fresh patch | skip duplicate, execute patch through SafeExecution |
| repeated equivalent `run_tests` | do not rerun; return structured prior observation and continue |
| repeated destructive/control action | reject/fail fast; do not execute later calls |
| two complete repeated/cached turns | stop as `NO_PROGRESS` or existing `REPEATED_ACTION` taxonomy after all safe results |

## Compatibility

- `ProgressPolicy` ratios remain 40%/70%/85%; only mechanical turn accounting
  changed.
- CompletionGate, `submit_result`, finalization reserve, and terminal settlement
  are unchanged. Completion-ready optional batches use the same turn-level
  bound and structured `completion_guidance_ignored` origin.
- Tool-call budget is not increased. Budget-rejected calls do not invoke a
  backend or consume extra execution allowance.
- Native tool calling and provider/runtime double IDs are unchanged; every
  considered valid call receives its matching ToolResult.
- SafeExecution and sandbox policy are unchanged.
- Session's existing cumulative step/tool/source facts remain durable. The
  mechanical stall streak and new batch-accounting counters remain run-local
  derived control state, as the prior cached guard already was.

## Failure origin and metrics

`StopReason.NO_PROGRESS` remains stable, while `failure_origin` distinguishes
`cached_batch_stall`, `empty_tool_batch`, `empty_model_turn`, and
`completion_guidance_ignored`; repeated stalls also record an explicit repeated
origin.

Accounting semantics are:

- `declared_tool_calls`: provider-valid calls declared in accepted batches;
- `processed_tool_calls`: calls given a terminal Runtime disposition and
  correlated ToolResult, including explicit rejection;
- `rejected_tool_calls`: processed calls refused before backend execution;
- `unprocessed_safe_tool_calls`: known non-completion calls whose backend was
  not invoked because a safety/budget decision rejected them.

The Eval/stability path also records
`mechanical_no_progress_failure_count`, `source_no_progress_failure_count`,
`repeated_action_failure_count`, `batch_premature_stop_count`, and
`progress_guard_unprocessed_safe_tool_call_count`. Stability checks the latter
two are zero. It does not require mechanical no-progress failures to be zero,
because two complete stalled turns are a legitimate guard outcome.

## Trade-offs

Turn-level aggregation retains a heuristic definition of novelty; it does not
understand whether a fresh read is useful. Returning a prior large test result
for a duplicate can still consume context, although it avoids an expensive
execution. Run-local accounting is intentionally not a new Session schema.

## Limitations

- Turn-level stall detection remains heuristic.
- `ProgressPolicy` still measures source-state progress rather than semantic
  task completion.
- External LLM reasoning variance remains possible; F03 may still fail for a
  genuine reasoning error.
- No deterministic 100% success claim is made.
- Environment-inspection caching and stdlib/project/sandbox portability
  classification remain deferred P2 work.

## Interview Version

Native tool calling exposed an old control-flow assumption: one assistant turn
was treated like one tool call. A cached first call could terminate the whole
turn and discard later fresh work. I kept per-call safety and duplicate
detection, but moved the stall decision to the completed safe batch: cached
calls are skipped with correlated results, a fresh observation prevents a pure
stall, and two fully mechanical turns still stop. Eval now distinguishes a
legitimate mechanical stop from Runtime-dropped safe calls without parsing
error strings.
