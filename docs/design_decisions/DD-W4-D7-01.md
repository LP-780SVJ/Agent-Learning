# DD-W4-D7-01: Oracle-Driven Agent Evaluation

## Status

Accepted, partially implemented.

## Context

CodeTeam needs a way to decide whether an autonomous coding task succeeded. The agent's own final message is not enough: it can misread tool output, pass tests and then modify files again, or claim success without satisfying the actual user-visible requirement.

## Decision

Use an external evaluation harness as the authority for task success.

Success is defined as:

```text
acceptance_passed
AND regression_passed
AND within_budget
AND security_passed
```

The agent is the actor. The eval harness is the judge.

## Alternatives

### A. Trust the agent final answer

Simple, but it allows self-grading and false positives.

### B. Trust tests executed inside the agent loop

Better, but still incomplete. The agent may run the wrong tests, misread output, or change files after the test command.

### C. Freeze final workspace and grade externally

More work, but it separates execution observations from final evaluation evidence.

## Consequences

- Eval tasks need hidden acceptance commands and visible regression commands.
- Every task must start from a fresh, fixed repository state.
- Metrics must come from structured results, not manual terminal copying.
- Safety violations count as task failure even if functional tests pass.

## Current Evidence

- Retrieval eval already follows dataset/result/manifest separation.
- CLI/session/sandbox tests verify runtime invariants independently of agent claims.
- Week4 Day7 adds `evals/week4/agent_task_suite_v1.jsonl` as a 15-task suite draft.

## Limitation

The full 15-task actor/judge benchmark is not yet run because the current `codeteam run` path still uses `MockPlanner` and does not produce real patches from an LLM-backed actor.
