## Problem

CodeTeam 的 Task 执行可能持续数十分钟、跨越多次模型调用与文件修改。如果 Python 进程在中途消失（用户 Ctrl+C、SIGKILL、断电、Python crash），如何让**另一个新进程**接续工作，而不是从零重来？

这个问题的本质不是"存点什么"，而是**存什么的边界**：

```text
Task / Plan / Usage / Worktree / Checkpoint / Provider 标识 → 进程死后必须仍在
ModelClient / Popen / Lock / GitWorkspace / Docker handle  → 绝不可"存"
```

Resume 的正确公式（day4 §三）：

```text
Resume = Durable State + State Reconciliation + Runtime Reconstruction
```

而不是"把 Agent 对象序列化回来再反序列化"。

## Context

Day 1~3 已建立 TaskSpec→Plan 状态机、Verify→Repair 闭环、Typed Error Recovery——全部活在进程内存。W4D3 验收遗留三项 Day 4 范围债务：K1（VERIFYING 无 PAUSED 转移）、K2（恢复动作接线，留 Day 5）、K3（PAUSED 恢复面缺 PLANNING）。

已有资产（实现前核实）：

- `task/models.py` TaskSpec、`planning/models.py` Plan/PlanStep —— 均为 Pydantic BaseModel，可直接嵌套序列化
- `failures/models.py` AgentFailure —— **已预留 `session_id` 字段**，`cause` 已 `exclude=True`（序列化安全）
- `git/models.py` WorktreeInfo、`git/checkpoint.py` CheckpointManager（`list_checkpoints()` 可校验链；state_root 强制在 workspace 外）
- `usage/` UsageTracker/UsageRecord —— dataclass、ephemeral 聚合器（**不能**直接序列化）
- 工业背景（day4 §一）：Codex 的 `thread/start|resume|fork` 分离且 required MCP 初始化失败时 resume 直接失败；Claude Code 持续写本地 transcript 并用运行中 Session 文件检测并发/Crash；Copilot CLI 完整 Session 落文件 + SQLite 派生索引（索引损坏可从文件重建）

## Requirements

1. 进程消失后，新进程仅凭磁盘状态即可理解"做到哪了"（Task/Plan/Usage/Worktree/Checkpoint/ActiveOperation）
2. Ephemeral Runtime Object（连接/子进程/锁）绝不进入持久化格式，Resume 时从配置**重建**
3. 预算/停止条件计数（tokens/cost/repair_attempts）必须 durable——否则 Resume 即绕过预算
4. Provider/model 标识 durable——否则事后归因（"这个 Patch 是谁生成的"）不可能
5. Resume ≠ load：必须对账持久化期望与外部现实（repo/worktree/checkpoint/provider）
6. 不安全/不一致时 fail closed（stale RUNNING、drift、terminal、concurrent）
7. 秘密（API key、source_message、metadata）不得落盘

## Alternatives

### Option A: Serialize the Live Runtime（pickle.dump(agent)）

- **优点**: 表面上"一行解决"——Agent 对象含 ModelClient/Plan/Counters/Context，pickle 似乎什么都有；第一版代码最短
- **缺点**（day4 §七十五~七十九逐一验证）:
  - socket/Popen/Lock/HTTP connection 对应**旧进程**，新进程中无意义，反序列化出废对象
  - 与代码实现强耦合：重构 `Agent.model` 字段后旧 pickle 加载即碎；无 schema 演进通道
  - 二进制不可观察：无法 `cat session.json` 直接知道当前 Plan/Worktree/状态，Debug 成本高
  - 安全性：官方文档明确警告 pickle 反序列化可执行任意代码——没有必要让 Agent State Format 建立在可执行格式上
  - 无法做 State Reconciliation：pickle 里没有"期望的 worktree HEAD"这类对账基线的显式表达

### Option B: Durable Domain State + Runtime Reconstruction（选定）

持久化显式 Domain State（JSON），Resume 时经 load 闸门 → 锁 → 对账 → 重建 Runtime：

- **优点**: 可观察（cat 即读）、可演进（schema_version + Migration）、安全（纯数据）、支持 Reconciliation（字段即对账基线）、Provider 解耦（存 provider_id 而非连接对象）
- **缺点**: 需要显式建模每个 durable 字段（~12 个模型）；需要重建逻辑（RuntimeFactory）；需要 schema 版本纪律；比 pickle 多写代码

## Decision

**采用方案 B：Durable Domain State + Runtime Reconstruction。**

```text
                    SessionService
        ┌────────────┬─────────────┬──────────────┐
        ▼            ▼             ▼              ▼
  JsonSessionStore  Reconciler   RuntimeFactory  WriterLock
   "怎么读写"     "记忆vs现实"    "重新搭机器"    "single writer"
        │
        ▼
.codeteam/sessions/<ses_xxx>/
├── session.json   Atomic Snapshot（Resume Source of Truth）
├── events.jsonl   Append-only 审计史
└── context.json   派生 context metadata（Day 5 升级）
```

## Why

1. **Crash Consistency** — atomic write（tmp+flush+fsync+replace）保证任意崩溃点磁盘上是完整旧快照或完整新快照（R6 fault injection 实证）
2. **可观察/可调试** — session.json 人类可读，`cat` 即知当前状态；这是 pickle 不具备的运维性质
3. **Schema 演进通道** — schema_version 闸门把"旧格式"与"损坏"严格区分（R5），未来 MigrationRegistry 有插槽
4. **对账可行** — WorktreeRef 的 last_known_* 字段本身就是对账基线；pickle 对象无此显式表达
5. **预算不可绕过** — SessionUsage durable（F11 跨进程证据）；repair/retry counter 同理
6. **安全边界** — 纯数据格式 + 序列化边界脱敏 + path traversal 守卫（R4）；持久层不成为 Credential Database
7. **Provider 解耦** — 存 `provider_id/model_id`（R18：不可用时 RECOVERY_REQUIRED，不静默换模型），为 Day 5 切换铺路

## Trade-offs

- **重建逻辑成本**：RuntimeFactory/Reconciler 是 pickle 方案没有的显式代码。已接受：这正是 State Reconciliation 的价值所在（day4 §五十：`/tmp` 被清理后 JSON 读得出来但实际无法恢复——Reconciliation 解决"记忆和现实一致吗"）
- **多文件非事务**：session.json/events.jsonl/context.json 三文件无跨文件原子性。已接受：明确 session.json = Source of Truth，events 丢失一条不损状态（DD-W4-D4-02 详述）
- **对账探测有成本**：每次 resume 跑 git 探测（common_dir/HEAD/dirty/cat-file）。已接受：Crash Recovery Latency 是周度 Benchmark 的既定测量项；probe 函数纯读无副作用
- **内存游标领先磁盘**：`last_event_seq` 在内存推进、save 时对齐——调用方必须用 service 返回值继续（闭包旧引用会落后）。已在 docstring 成文并测试
- **R23 未完全闭环**：跨进程 resume 已有（R21 新进程恢复六项），但真实 SIGINT kill→resume 留 Day 6 CLI（Ctrl+C 是 CLI 场景）——PARTIAL，非本 DD 缺陷

## When to Revisit

- **周度 Benchmark 后**：save/load P50/P95、Resume-to-ready、Crash Recovery Latency 出炉 → Evidence 升级判定
- **周度 Ablation 后**：No Persistence vs Persistence（Rework Ratio / time to next productive action / repeated tokens）验证 Durable State 的实际价值量
