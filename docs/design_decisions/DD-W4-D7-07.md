# DD-W4-D7-07: Provider-Neutral Agent Turns and Native Tool Transport

## Status

Accepted on 2026-08-28.

## Problem

The production `ModelClient` still exposed `complete(messages) -> text`, even
though `CodingAgentRuntime` had become an iterative tool-using agent. The
OpenAI-compatible request omitted native tools and an output budget, response
parsing retained only `message.content`, and tool observations were converted
back into `role=user` JSON. A semantically correct patch action could therefore
be truncated before it became a `ToolCall`; `SafeExecutionService` never saw
the patch.

The root cause was not that the model could not write the patch:

> Agent action transport was incorrectly modeled as free-form text generation.

## Alternatives

1. Continue strengthening the JSON/DSML parser. This helps legacy providers but
   cannot recover missing bytes or represent provider finish state.
2. Add only `max_tokens`. This reduces some truncation risk but leaves actions,
   call correlation, empty native content, and tool results under-modeled.
3. Parse OpenAI/DeepSeek response fields directly in `CodingAgentRuntime`. This
   makes the happy path work but leaks provider wire details into the domain
   Runtime and breaks provider neutrality.
4. Introduce `ModelRequest -> Provider Adapter -> ModelTurn`. This purchases
   native tools, explicit input/output budgets, typed finish states, usage and
   provider evidence while keeping Runtime semantics provider-neutral.

## Decision

- `ModelRequest` carries messages, existing `ToolRegistry` descriptions,
  `max_input_tokens`, `max_output_tokens`, context window, safety headroom,
  native-tool preference, and provider-neutral reasoning/response options.
- `ModelTurn` carries text, the existing `ToolCall` schema, normalized finish
  state, original finish reason, usage, model/provider attribution, response
  ID, actual response mode, incomplete reason, and system fingerprint.
- `codeteam.llm.openai_compatible` exclusively owns HTTP payloads, native tool
  schema conversion, response parsing, capability fallback, and retry metadata.
- Production prefers native tools. JSON, fenced JSON, DSML, and protocol repair
  remain as a fallback codec when native tools are unavailable or a final
  response is textual.
- `ToolCall.call_id` remains Runtime-owned. `provider_call_id` is an opaque
  transport correlation. Native assistant messages and tool observations
  durably preserve both; only the provider ID is serialized as wire
  `tool_call_id`.
- `finish_reason=length`, content filtering, malformed native arguments, and an
  empty turn are typed before the textual parser. A native call with
  `content=None` is valid.
- `context_budget` is explicitly an input budget. Request validation reserves
  output tokens and safety headroom, and the provider adapter rejects an
  oversized serialized request before HTTP.
- DeepSeek/OpenAI-compatible native smoke configuration disables reasoning for
  this first transport milestone. Reasoning continuation is not implemented.

## Invariants

- Provider wire envelopes never become AgentLoop control input.
- Native actions execute at most once; native calls take precedence over text
  in the same turn.
- Provider IDs never become ToolRegistry, event, repetition, or
  SafeExecution identifiers.
- Every native `role=tool` message has its corresponding structured assistant
  call, including after Session resume and compaction.
- `length` and malformed native arguments invoke no tool backend and consume no
  textual protocol-repair budget.
- `apply_patch` and `run_tests` continue through the existing
  `SafeExecutionService` lanes.

## Trade-offs

- `ToolCall.call_id` is optional at the provider-neutral turn boundary and is
  made mandatory by the Runtime before registry execution. This is a small type
  compromise that avoids creating a second tool-call schema.
- A legacy `complete()` compatibility lane remains for existing planners,
  fakes, recorded sessions, and textual-only providers. It increases temporary
  surface area but avoids a repository-wide breaking migration.
- Input token estimation still uses the replaceable local approximate counter;
  it now counts UTF-8 serialized messages, structure, and tools rather than
  message character content alone. Provider-tokenizer precision remains future
  work.

## Verification

- OpenAI-compatible adapter tests cover native payload/schema generation,
  `max_tokens`, reasoning disabled, usage/evidence, capability fallback,
  `length`, empty-turn retry, malformed arguments, and pre-HTTP input budget.
- AgentLoop tests cover native happy path, dual-ID round-trip, duplicate native
  plus textual action, incomplete/truncated/invalid turns, and unknown tools.
- Coding Runtime integration proves native patch and test calls enter
  `SafeExecutionService.execute_patch()` and `execute_command()` exactly once.
- Session tests prove native assistant/tool history and dual IDs survive JSON
  persistence, resume, durable tail selection, and compaction atomically.
- Full offline suite: `1308 passed, 6 skipped`.
- B01 real-provider smoke: `NOT_RUN_BY_CODER`.
- 11-task benchmark, native/text ablation, and production transport metrics:
  `NOT_RUN`.

## Limitations

- Completion ownership / `READY_TO_FINALIZE` remains pending. A correct patch
  can still fail if the model repeats a verified action instead of submitting
  the existing final output.
- Full reasoning-content continuation and provider-specific tokenizer support
  are not part of this change.
- Native tool capability still requires a user-run B01 smoke against the
  configured real provider before any benchmark claim.

## Interview Version

The model was finding the right file and proposing the right patch, but our
client forced the action through free-form JSON text and sometimes lost the
closing envelope. I changed the boundary from text completion to
`ModelRequest -> ModelTurn`: provider adapters normalize native tool calls,
finish state, usage, and opaque call IDs; the Runtime generates its own trusted
ID and continues through the same safe execution layer. Text JSON/DSML remains
only as compatibility fallback. This moved the failure boundary from “could a
parser reconstruct an action?” to “did the provider produce a valid typed
turn?”.
