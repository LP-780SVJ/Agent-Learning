# DD-W4-D5-02: Provider-neutral Model Runtime

- **日期**: 2026-08-21
- **模块**: `codeteam/llm/base.py`, `codeteam/llm/registry.py`, `codeteam/llm/switching.py`, `codeteam/agent/orchestrator.py`
- **状态**: Accepted（MVP 实现完成）
- **Evidence status**: PROPOSED（A4 架构度量周度执行后再升级）

---

## Problem

Coding Agent 不能把 OpenAI、Anthropic、本地模型或企业网关的分支散落在 AgentLoop、Planner、RepairLoop 中。否则新增一个 provider 就会改 core runtime，恢复、观测、测试也会变成 provider-specific。

同时，模型切换不能在一个 turn 中途生效。否则同一轮的输入、工具调用、输出可能来自不同模型，审计和错误归因都会失真。

## Context

Week4 Day5 引入 Provider Registry、ModelSelection、ModelMetadata 和 ModelSwitchService。Day4 Session 已经持久化 provider_id / model_id，Day5 需要把它升级为 provider-neutral runtime 边界。

## Requirements

1. AgentLoop / Planner / RepairLoop 只依赖 `ModelClient` Protocol。
2. Provider 和 Model 是两条独立轴：Provider 是连接方式，Model 是能力与容量。
3. ModelMetadata 以 `(provider_id, model_id)` 为键，因为同名模型在不同部署下可能有不同 window、价格和能力。
4. API key 只存在环境变量和 client 内存中，不进入 Session / events。
5. Turn 内 selection 不可变；mid-turn switch 只能排队到下一个 turn boundary。
6. 切换失败必须 fail closed，旧 selection 保持不变。
7. context budget 来自 ModelMetadata，而不是模型名字符串猜测。

## Alternatives

### Option A: Provider-specific Branches in Core Runtime

- **优点**: 初期直观；每家 provider 快速硬编码。
- **缺点**: core runtime 膨胀；新增 provider 需要改 AgentLoop/Planner/RepairLoop；测试矩阵扩大；resume 归因复杂。

### Option B: One Universal Client with Raw Dict Config

- **优点**: 表面统一；配置自由。
- **缺点**: 缺少类型约束；credential、capacity、capability 容易混在一起；错误分类依赖运行时猜测。

### Option C: ModelClient Protocol + ProviderRegistry + Transactional Switch（选定）

- **优点**: core runtime 只看 Protocol；provider 注册在边界层；switch 有事务语义；metadata 可用于预算。
- **缺点**: 需要 registry、selection、metadata、switch outcome 等额外模型。

## Decision

采用 **Provider-neutral Model Runtime**：

```text
AgentLoop / Planner / RepairLoop
  -> ModelClient Protocol
  -> ProviderRegistry
  -> ProviderConfig.client_factory
  -> ephemeral provider client
```

Turn 内 `ModelSelection` 不可变。切换请求在 turn 中途只能排队，下一 turn boundary 才验证和应用。

## Why

1. **架构隔离**：core runtime 不知道 provider 细节。
2. **Resume 可重建**：Session 存 durable selection，新进程通过 registry 重新 build client。
3. **审计可归因**：turn.started / turn.completed 记录 provider_id / model_id。
4. **预算准确**：context budget 由 ModelMetadata 推导。
5. **失败安全**：invalid provider/model/credential/capability 时旧 selection 不动。

## Consequences

- 新 provider 应通过注册 ProviderConfig + ModelMetadata 接入，而不是修改 AgentLoop。
- API key 不得进入 Pydantic durable model。
- ModelSwitchService 必须维护 turn boundary，不允许中途替换 current client。
- SessionService 与 CLI 层后续要把 durable provider/model selection 接入 registry。

## When to Revisit

- A4 架构度量执行后，统计新增 provider 需要改多少 core 文件。
- 如果某 provider 的 capability 无法表达在 ModelMetadata 中，再扩展 metadata schema。
- 如果 turn-level usage/cost 归因需要更细粒度，应把 usage tracker 快照加入 turn.completed payload。
