# FC-W4-D7-04: F03 Analysis Paralysis Without Source Progress

## Evidence

- Run: `evals/week4/agent_runs/completion_gate_11task_20260829_171835`
- Task: F03
- Outcome: `failure_category=max_steps`
- Consumption: 20 model turns, 37 tool calls
- Source activity: 0 patch attempts, 0 changed files, empty final diff
- Infrastructure: sandbox and Python/pytest preflight passed; provider/protocol failures were zero

## Timeline

Initial context and subsequent reads exposed the dispatcher, the explicit-false
test, the feature flag file, and the requirement to preserve behavior when the
flag is absent. The model repeatedly searched/listed/read different paths and
ran the visible tests. It became stuck on whether PyYAML happened to exist in
the Docker environment. At turn 19 it articulated a viable minimal fallback
parser approach, but spent turn 20 reading/searching again and reached the step
limit without a source edit.

## Root-cause layers

1. Primary: Runtime had no source-progress-aware intervention. Diverse tool
   calls evaded repeated-action guards even though the program never changed.
2. Secondary: Runtime lacked a narrow way to ask the actual verification image
   whether one module/executable was available.
3. Efficiency contributor: complete initial context could be reread and
   retransmitted, increasing pre-edit work.

This was not a retrieval failure: the decisive code and test were available.
It was not a provider, protocol, verification, scratch, completion-gate, repair,
or security failure. The executable idea at turn 19 also proves that environment
inspection alone would not guarantee action; progress control is the primary fix.

## Resolution

- `ProgressTracker` adds two proportional soft checkpoints and a typed terminal
  `no_source_progress` pause without forcing a patch.
- `inspect_environment` supplies fixed Docker evidence while preserving the
  arbitrary `python -c` denial.
- `InitialContextSnapshot` safely reuses only complete current-version files.
